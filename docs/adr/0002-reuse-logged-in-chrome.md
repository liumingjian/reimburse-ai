# 复用用户已登录的 Chrome，由用户自行完成 ERP 登录

> **Status: superseded (2026-09-15, #197).** Superseded by ADR-0016: the server-owned ERP executor drives a dedicated Chromium profile under the app data directory; no Skill, no kernel copy (deleted in #197). Paths below point into git commit `50931a3`, the last one that has the Skill-era code.

> **状态：已修订（2026-09-11，见[本地报销应用](../design/standalone-app.md)）。** 继续有效：内核经 CDP 驱动专用 profile 的 Chromium、用户自己登录 ERP、Node 内核零 npm 依赖。「去报销」即执行自动填报，此前「当前阶段不执行填报」的说法作废。下文中「Skill 引导用户」「内核随 Skill 拷贝」及 MarkItDown 运行时相关表述均为 Skill 时期的历史记录；普通页面用系统默认浏览器、ego 仅供自动化 QA 的规则见 AGENTS.md。

ERP 自动化不自带浏览器，而是接管用户自己的 Chrome：Skill 引导用户以远程调试方式启动浏览器，**用户自己登录 ERP**，随后内核通过调试协议独占控制该浏览器完成上传、导入和保存草稿。

这样选有三个理由：不需要下载几百 MB 的浏览器运行时（而 Claude Code 插件与 Skill 都没有任何 postinstall 机制，实测确认插件安装只是文件拷贝，连声明的 npm 依赖都不会装）；ERP 凭据从头到尾留在用户手里，baox 不接触账号密码；以及它天然契合共识里「用户只需完成一次会话授权、使用已登录的 ERP 浏览器会话」。

## Considered Options

- **自带 Playwright 浏览器**：能力最完整，但首次要下载几百 MB 且无处挂载这一步，与「员工电脑可能没有任何编译或运行环境」的约束冲突。
- **用 Claude in Chrome 扩展让模型直接操作浏览器**：这是官方一等公民，也是「全部用 Skill 实现」的真实路径，但它是模型驱动的，会使 `ERP 动作尝试`、`ERP 对账` 和 `ERP 写入结果未知` 失去可信记录 —— 而共识明令禁止「重放上传试试看」。写入路径否决。

## Consequences

- **用户声明「已授权」不成立授权。** 内核必须先做只读探测：确认已登录、确认登录身份与本任务的员工身份一致、确认能进入费用报销单页面。身份不一致是**硬阻塞**，不允许用户确认「就用这个身份」—— 报销主体错了无法靠后续步骤补救。
- 自动化期间使用独立的浏览器 profile 与用户日常浏览隔离，并在每个动作前后做只读回读校验；仅靠「请用户不要碰这个窗口」不够。Skill 需在开始时明确告知不要操作该窗口，结束时明确交还控制权。
- 环境依赖无法消除，只能收敛成一次引导：`baox-setup` 负责检测并在用户确认后安装 Node、引导以调试方式启动 Chrome，并做环境自检。失败提示必须具体到可操作。
- 内核安装在 baox 自己的用户级数据目录（macOS 为 `~/Library/Application Support/baox`）下的 `runtime/`，不从 Claude Code 的 Skill 目录直接运行 —— 后者会随更新被重建，且多个 Skill 各夹带一份会造成版本漂移。离线分发时每个 Skill 目录携带一份内核源码，由 `baox install-runtime` 拷进 `runtime/`，三个 Skill 统一调用那一份。
- v1 按跨平台设计，但**先只在 macOS 上验证并发布**。原生 Windows 额外需要 Git for Windows（否则没有 Bash 工具）与 Node，两者都要引导；在真机跑通前不对员工宣称支持 Windows。

## 补记（2026-09-05，实测后修订）

- **Node 内核零 npm 依赖。** Node 21+ 自带全局 `WebSocket`，CDP 不再需要 `ws` 之类的包，HTTP 服务器也是内建的。因此 Node 内核不需要 npm 安装或管理员权限，内核可随 Skill 文件拷贝运行。文本 PDF 的 MarkItDown 依赖不属于这条承诺，必须按 [ADR-0011](0011-markitdown-agent-pdf-candidates.md) 预置并锁定 Python/uv 运行时；内核要求 Node ≥ 21，`doctor` 对此硬检查。
- **独立 profile 与用户日常 Chrome 可以共存。** 在 mac 上实测：用户 Chrome 的 32 个进程照常运行，`--user-data-dir` + `--remote-debugging-port=9333` 另起一个实例，调试端口只 LISTEN 在 `127.0.0.1`。这也意味着用户需要在这个专用 profile 里登录一次 ERP（登录态随 profile 持久化，不是每次都登）。
- **登录态识别不能靠通用启发式，只能用 ERP 自己的结构信号。** 实测 K3Cloud 8.2.0：登录页 URL 里没有 `login`；**已登录的主控制台里有 4 个隐藏的 `input[type=password]`**（改密弹窗），所以密码框永远不能当未登录信号；`Getk3cloudloginInfo()` 在命名用户登录下返回 `null`，没有现成的身份全局变量；首屏加载慢，`document.readyState` 会长时间停在 `loading`。
  最终采用的两个信号缺一不可：主控制台的 `span.kd-mainconsole-usernametext`（显示名，会话信号）与 localStorage 的 `k3cloudloginInfo.user`（登录账号，身份信号）。**localStorage 单独不算数** —— 它记的是"最近一次登录用的账号"，退出登录后依然留着，只能用来标定身份，不能用来证明会话仍然有效。读不出用户名元素一律归为硬阻塞。
- **探针输出去掉 URL 的 query。** K3Cloud 的 `_cnneptstate_` 参数携带会话态，属于契约里禁止落盘的短时效 URL，因此只回报 origin + pathname。
- **本地选择界面采用前台阻塞模型。** 内核监听临时端口（不可能冲突）、阻塞等待提交、拿到结果自行退出。实测提交后端口无残留监听、进程退出。这样就不存在「会话结束后怎么收」的问题，也不需要守护进程。
- **个人 Skill 的 hooks 生效，第三层门禁成立。** 交互式实测：`~/.claude/skills/` 下的非插件 Skill，其 frontmatter 里声明的 `PreToolUse` hook 确实注册并硬拒命中的命令 —— 命令不执行，模型侧只拿到一条 hook error，没有任何绕过口子。这意味着放弃插件后纵深防御并没有丢：ADR-0001 里的三层门禁（Skill 指令 / hooks 硬拦 / 内核 exit 2）在离线 Skill 形态下完整可用。安全地板仍然是最底下那层。

## 补记（2026-09-07，首次真机试用后修订）

- **身份一致不再靠一个传进来的名字，改为一次性的个人绑定。** 原来的做法是 `probe --expect <名字>`：Agent 把一个字符串传给内核，内核拿它和 localStorage 里的显示名**或**登录账号做不区分大小写的比较，任一命中即通过。实测下来三处都不成立：真机身份是显示名「刘明建」、登录账号 `luo.liu`，用户会说前者而说明书的例子写的是后者，两边都可能对不上；"任一命中"让登出后仍留在 localStorage 里的账号有机会在会话已失效时误判为通过；而这个字符串本身是经 Agent 转述的，报销主体一旦错了，发票就写进了别人的单子，不可撤销。
  现在改为：内核自己从 ERP 页面读出身份，在一个只显示、不接受输入的本地确认页上摆给用户，用户点一次「是我本人」才落盘（复用本文上一条补记里的前台阻塞模型）。**判据是登录账号 + 账套**，换账套等于换一整套主数据；显示名只展示不作判据，因为 ERP 里改得动它。会话信号和身份判据从此是两层：探针只回答"谁登录着"，绑定回答"他是不是该报销的那个人"——两者的处置完全不同，一个是让用户去登录，一个是让用户去换人。
- **身份不一致仍是硬阻塞，但"改绑"这条路是有的，且只在没有进行中任务时开。** 上面 Consequences 里写的「不允许用户确认『就用这个身份』」，本意是不许在一次报销当中把主体换掉，这一点不变：有进行中任务时改绑一律拒绝。但一台机器换人使用（换员工、离职交接）是真实存在的，逼用户去删数据目录才是更坏的答案。所以放宽的边界是**任务边界**，不是用户的口头确认——这和「常驻城市」的做法一致：重新确认只对此后新建的任务生效。
- **排障旁路走环境变量，不做成命令行开关。** `BAOX_SKIP_IDENTITY_CHECK=1` 只能由人在终端里敲出来，模型写不出它；而且一旦生效，每一次输出都把它标出来——一份看不出自己被旁路过的记录，比没有记录更糟。

## 补记（2026-09-07，前台阻塞模型的一处遗漏）

- **前台阻塞的页面必须由内核自己打开。** 原来的做法是内核把地址写到 stderr，Skill 说明书让 Agent「把 stderr 上的地址给用户」。这条指令**不可能被执行**：命令阻塞在前台，Agent 在它返回之前既读不到 stderr 也说不出话，所以"把地址给用户"这一步永远发生在用户已经干等完之后。真机试用里的表现就是用户登录完之后对着一个没有任何输出的会话等了 6 分钟。现在内核在 `onReady` 时用系统默认打开方式（macOS `open` / Windows `start` / Linux `xdg-open`）直接把页面弹出来，stderr 上的地址退居兜底。打不开不算失败——它只是回退到原来的路径。
  说明书那一半也补了：**要在运行这条命令之前**告诉用户页面即将弹出，因为运行之后就没有机会说了。
- **旁路开关是 `BAOX_NO_AUTO_OPEN=1`**，给无头环境和自动化用。前台阻塞、临时端口、提交即退出这三条性质都不变。

## 补记（2026-09-07，1.0.0：内核就地运行，数据目录搬到 `~/.baox`）

- **上面 Consequences 里「内核安装在数据目录的 `runtime/`，不从 Skill 目录直接运行」这一条作废。** 内核现在就地运行，`baox` 展开成 `${CLAUDE_SKILL_DIR}/kernel/bin/baox.mjs`，`install-runtime`、`launch.mjs` 和整套版本闸一并删除。原来的理由是"多个 Skill 各夹带一份会造成版本漂移"，但那道闸挡不住真正发生过的事故：个人目录里的旧 Skill 静默遮蔽项目目录里的新 Skill 之后，旧 Skill 配旧内核完全自洽，闸门永远不触发（见上一条补记）。它挡住的只是安装步骤本身漏跑，而那个步骤是它自己引入的。就地运行之后，跑的是哪一份内核和跑的是哪一份 SKILL.md 从此是同一个问题，不可能对不上。
- **版本号不再是闸，只是标签。** `50931a3:kernel/VERSION` 继续由 `doctor` 报出来，用途只剩把用户报回来的问题钉到具体某一版。跨版本的兼容性判据改为数据目录里的 `schemaVersion`（见 [state-machine.md](../design/state-machine.md) 的 `schema_too_new`）——该判的是数据格式，不是代码版本。
- **数据目录从 `~/Library/Application Support/baox/` 改到 `~/.baox/`**（`BAOX_HOME` 覆盖不变）。理由是用户自己找得到、打得开：这个目录里装着他本人的发票副本，出问题时第一句话应该是「打开 `~/.baox` 看看」。0.9.x 的既有数据在第一条命令上自动**拷**过去（不是移动），迁移只做一次，并在那条命令的输出里报 `migrated: { from, to }`。旧目录原样留着，装回 0.9.x 仍然可用——升级要能回滚，代价只是磁盘上多一份 `chrome-profile/`。

## 补记（2026-09-07，1.0.0：本地页面收窄到两处）

- **本地页面只剩两处：重新绑定身份，和浏览完整项目目录。** 其余用过本地页面的环节全部下线：读数确认改走**终端表格**（`confirm_table`），逐段分摊改走**对话提问**（`ask_user`），通用单选页整个删掉。理由是页面这条路有一段绕不开的代价——命令在前台阻塞、用户要切窗口、Agent 在它返回之前一个字都说不出来（见上面那条补记）。这个代价对"确认一张读数表"来说太贵了：那件事在终端上一次就能问完，而且问完还留在对话里，用户回头翻得到。
- **留下的那两处是留对了的。** 重新绑定身份要的是一次**不可撤销**的确认，它必须发生在一个内核观测得到的事件上，而不是对话里的一句"是我"；浏览完整项目目录要的是滚动、搜索和一次看几十行，终端给不了。判据是"这件事离开页面就做不成"，不是"页面看起来更好看"。
- **`serve.mjs` 的自动弹窗保留**，就是给这两处用的。

## 补记（2026-09-07，1.0.0：更正——`${CLAUDE_SKILL_DIR}` 并不存在）

- **上一条补记里「`baox` 展开成 `${CLAUDE_SKILL_DIR}/kernel/bin/baox.mjs`」这个说法不准确。** 真机实测（Claude Code 2.1.263）：`CLAUDE_SKILL_DIR` **不在 Bash 工具的环境变量里**。三份 SKILL.md 里那个写法之所以看起来能跑，是因为模型自己把它换成了绝对路径，不是 shell 展开的。见 [skill-declared-hooks.md](../research/skill-declared-hooks.md)。
- **"内核就地运行"这个决定本身不受影响**——跑的仍然是 Skill 目录里的那一份，不可能和 SKILL.md 对不上。受影响的只是"入口那一行是怎么解析出来的"这个说法。

## 补记（2026-09-07，第二轮真机 QA：第一次认身份也搬进终端）

- **首次绑定改走终端表格（`confirm_table`），本地页面只剩改绑一处**（加上浏览项目目录）。
  上一条补记说"本地页面只剩两处：重新绑定身份，和浏览完整项目目录"，写的是**重新**绑定，
  而代码里首次绑定也在弹页面 —— `next.mjs` 的注释把它记成了"批次 5 的活"，然后没人做。
  QA 现场用户看到的就是它：流程刚开始就跳出一个浏览器窗口让他点「是我本人」。
- **搬过去没有丢掉任何东西。** 这条决定真正要守的是「**没有一个字符串经过模型的手**」，
  而不是「点击发生在页面上」：表里三行都是内核自己从 ERP 读到的，用户只能认或不认；
  回传时内核**重新读一次 ERP**，读到的人和用户刚才看过的那一个（凭据里记着的 account + tenant）
  对不上，这次点头当场作废。改绑仍然留在页面上：那是一次推翻已有绑定的动作，
  值得一次要人手敲 `confirm-identity` 的显式往返。
