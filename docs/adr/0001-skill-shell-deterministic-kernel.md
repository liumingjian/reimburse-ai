# 用户入口是 Skill，业务判定留在确定性内核

> **Status: superseded (2026-09-15, #197).** Superseded by the local app ([standalone-app](../design/standalone-app.md), ADR-0014 to ADR-0018): the Skill entry point and the Node kernel were deleted in #197; business judgement lives in the server (`server/src/`). Paths below point into git commit `50931a3`, the last one that has the Skill-era code.

> **状态：部分取代（2026-09-11）。** 「用户入口是 Skill」一半已被[本地报销应用](../design/standalone-app.md)取代：入口改为本机页面，页面输入是来源为 `user` 的候选，而非对话。「业务判定只在确定性内核」一半继续有效。继任 ADR 待补。

baox 的用户入口是 Claude Code Agent Skill，而不是员工直接使用的命令行工具：目标用户是公司内已经在用 Claude Code 的员工，让他们记 `baox run` / `baox resume` 这套命令和它们的失败语义没有必要，对话式引导才是更合适的前门。

但材料盘点、发票身份、重复判定、金额守恒、确定性校验、动作账本和 ERP 对账**不进入 Skill**，它们仍然是确定性可执行代码（内核）。理由是这些正是本项目的全部价值所在：设计共识明确要求「用户不能点击确认继续绕过重复」「不得由模型平均、按比例、按距离、按时长或编造金额」「按钮点击成功不等于上传成功」。这些约束的执行者如果是模型对一段 Markdown 的服从度，那它们就不是约束，只是建议；而报销数据要进财务和审计。

## Considered Options

- **全部由 Skill 执行**（判定和放行都由模型在对话中完成）：与上述共识正面冲突，否决。
- **保持面向员工的 CLI 产品**：需要单独安装、跨 macOS/Windows 分发、命名和终端教学成本，而收益只是一个员工本来就不想学的界面。作为**产品界面**否决；作为内核的内部调用协议保留。

## Consequences

- Skill 的职责被限定为三件事：把自然语言意图翻译成内核调用、把内核输出的待确认项解释给用户、把用户的口头纠正翻译成结构化纠正指令。它不判定、不计算、不裁决放行、不操作浏览器、不写 ERP。
- **用户的自然语言输入永远不构成业务事实。** 权威事实只能由内核从权威来源读取：任务选择的权威来源是本地 Web 的提交行为，ERP 授权的权威来源是对登录状态的只读探测。用户说「我填好了」「已授权」只是要求内核去读一次，不是确认本身。
- 门禁采用三层纵深，且**内核硬拒是地板**：内核在快照不满足时直接拒绝执行；`SKILL.md` 规定门禁结论只能引用内核输出原文；Skill 激活期间用 `disallowed-tools` 移走浏览器控制类工具。只靠后两层的设计不成立。
- 三个 Skill 按用户处境切分：`baox-setup`（引导式配置与环境自检）、`baox`（主流程）、`baox-recover`（中断恢复、`ERP 写入结果未知` 的只读对账、转人工）。`baox-recover` 允许的动作与主流程截然相反，必须独立。
- 三个 Skill 全部允许模型自动触发（model-invoked）。见下方 2026-09-07 修订。
- Skill 自身无状态；任务状态全部在内核的任务工作区里，每个 Skill 的第一个动作都是让内核读一次当前状态。
- v1 的业务 Web 界面只保留**一个**：任务选择。材料整理确认改由对话完成（待确认项逐条、异质、需要解释，对话更合适；项目归属同构、高密度、要批量应用且需要可审计提交，表格更合适）。原设计中的「整理纠正 Web」取消。
- Full Reset 另有一个内核本地确认页。它不接收任何业务事实，只让用户本人授权一次不可逆的本地清空；模型只能启动页面，不能提交确认。
- `docs/research/cli-name-candidates.md` 的筛选标准（长度、中文联想、易读性）随之失效，员工不再输入这个名字；该文档仅保留为历史记录。

## 2026-09-07 修订：改为允许模型自动触发

原文写的是「三个 Skill 全部禁止模型自动触发，只允许用户显式调用」，理由是这套流程会写入外部系统。
实现落地之后这一条站不住，现改为三个 Skill 全部 model-invoked。

**改的理由**：`baox` 必须能自主到达另外两个 Skill。第一是环境缺失时到达 `baox-setup`；第二、也是要紧的那条，
是任务派发过 ERP 写入之后到达 `baox-recover`。交接如果依赖用户记得敲 `/baox-recover`，那么最危险的那条路径
（发票已经被 ERP 消耗、单停在半成品状态）恰好是最容易漏掉的一条。禁止自动触发保护不了它，只是把风险移给了人的记性。

**原顾虑现在由更硬的机制承载**，而不是由「只能人来调用」承载：

- 内核硬拒是地板：快照不满足时内核直接拒绝执行，Skill 怎么被触发都绕不过去。
- 身份闸：任何读写 ERP 的命令先过只读身份探测，`matched` 之外一律硬阻塞。
- 工具层裁剪：`baox-recover` 的 `allowed-tools` 不含 `Read`（ADR-0010），`baox-setup` 的也不含。
  `baox` 保留 `Read`，因为看图读取那一个分支必须由模型亲自看图；它是内核唯一需要模型能力的地方。
  三个 Skill 都不带浏览器控制类工具。
- 提交即确认（consent）：写入外部系统的每一步都以本地 Web 的提交事件为唯一许可，模型触发不了它。

**保留的边界**：自动触发的是「对话表面」，不是「写入许可」。模型可以自己决定跑哪个 Skill，
但每一次外部写入仍然要过上面四层。
