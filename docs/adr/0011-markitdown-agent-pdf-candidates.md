# 文本 PDF 由 MarkItDown 转换，Agent 只提出候选

状态：已接受。日期：2026-09-09。

## 决定

文本 PDF 的主路径固定为：

`原始 PDF -> MarkItDown Markdown -> Agent 字段候选 JSON -> 内核确定性校验 -> 分类明细确认`

MarkItDown 只负责把文字材料转换成 Markdown，Agent 只解释字段并给出原文证据；内核继续拥有材料身份、范围、发票身份、金额、日期、事件、重复、分类和 ERP 放行的决定权。Markdown 是派生产物，不是新的原始材料。

Node 内核仍保持无 npm 依赖。MarkItDown 使用随 Skill 发布的 Python/uv 锁定运行时，转换命令通过 `uv run --locked` 同步依赖；首次运行可能联网下载软件包，转换材料在本机处理。评估使用的临时虚拟环境不构成部署路径。uv 不可用、同步失败或锁文件不匹配时，PDF 分支阻塞；插件及云端 OCR 保持关闭。

## 必须经过的闸

1. **原件身份。** 内核先固定当前材料的 `materialId`、原件 `contentHash` 和任务材料范围，再生成 Markdown。内核记录转换器版本、参数和 Markdown 哈希；Agent 不填写这些元数据。
2. **候选来源。** Agent 的来源标记为 `agent_from_markdown`。候选只能使用工单给出的封闭 schema；它不是已解析值，也不能把来源伪装成 `kernel` 或视觉读取。
3. **精确证据。** 每个非空字段都带绑定 Markdown 哈希的 1 基行标识和原文连续片段。跨行字段逐行给出片段并说明归并依据。内核逐条检查 quote 确实存在于对应行；模型手数的行号不构成证据。
4. **事实格式。** 金额保持两位小数字符串，日期保持真实材料日期，`issueDate` 不替代费用发生日；发票代码、号码等身份字段保留票面原生格式。明细金额不自动当合计，不补算，不因守恒缺口修改字段。
5. **确定性校验。** 内核拒绝未知字段、哈希不匹配、引用不存在、格式错误、非法日期、身份冲突、金额不守恒、声明段数不一致和逐段金额不完整的候选。引用存在不等于语义归属正确，歧义保留为待确认项。
6. **用户确认。** 候选通过校验后，继续材料证据关联、事件和分摊；用户必须完成 `classified_detail_confirmation`。分类明细确认前不得进入项目簿、项目归属或 ERP 就绪。

合并交通发票沿用当前内核规则：用户已给出的有效分摊优先；否则，行程单逐段金额与发票合计按分精确守恒时由内核核对采用，不能守恒时再向用户提问。Agent 负责提取，不决定采用或切分税额。材料、日期、金额、证据或任一哈希变化都会使旧候选和确认失效，并触发重新检查。

## 分支边界

- MarkItDown 转换失败、产物为空或缺少必要文字时，内核保留明确的 `blockedBy`/待确认项；Agent 不从文件名、尺寸、申请日期、开票日期或行程范围补造字段。
- PNG/JPG 继续使用视觉读取与用户确认的通道（ADR-0004）。只有内核发出 `read_images` 工单时才看图；视觉读数不能冒充 Markdown 候选。
- 没有可靠文字的 PDF 不自动当成图片，也不自动接入 OCR。用户需要提供可读原件，或按内核给出的阻塞分支处置。

## 依据与迁移

2026-09-09 的评估转换了 9 份 PDF 和 1 份 PNG。文本保留率支持这条主路径，但 Markdown 表格会断裂、串列，首轮盲测的业务值正确而证据行号错误；因此“转换成功”和“JSON 合法”都不能直接放行。生产迁移必须补齐锁定运行时、内核候选接收、quote/哈希/金额/日期校验和真实材料验收。

ADR-0003 标记为历史对照；其 Node 内核无 npm 依赖和空文本 PDF 阻塞范围仍有效。ADR-0004 继续负责图片视觉读取，ADR-0005 继续负责合并交通票逐段金额规则。
