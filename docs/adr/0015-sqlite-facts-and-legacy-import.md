# The local app keeps append-only facts in one SQLite file and imports only what outlives a legacy task

The new baox local app stores structured facts in SQLite and file bytes on disk, content-addressed, under a new data directory `~/.baox-app/`. Almost every table is append-only, each 报销任务 (reimbursement task) pins the rules it was created with by content hash, and a one-time import carries over from the legacy `~/.baox` only what still matters without its tasks: identities, 常驻城市 (home city), 个人项目簿 (personal project book), and the 发票占用 (invoice occupancy) of legacy tasks that touched ERP. Decided in [#151](https://github.com/liumingjian/reimburse-ai/issues/151).

## Decisions

- **Data directory.** One root, `~/.baox-app/` (`BAOX_DATA_DIR` overrides it for dev and tests only): `baox.sqlite` (WAL), `files/sha256/<ab>/<hash>`, `backups/`. Directories 0700, files 0600. A lock file allows one server process per directory. Personal settings (home city, identity binding, ERP username) are tables in the same database, not a config file; the ERP password stays in the macOS Keychain. It is a separate directory from `~/.baox` so that the import can read the legacy directory without ever writing to it.
- **Append-only by default.** Upload batches, materials, inventory versions, field candidates, 解析记录 (resolution records, which also carry pending-item answers), validation results, confirmations, ERP action attempts and their outcomes (an outcome is its own row), rule pins and audit events are insert-only; SQLite triggers `RAISE(ABORT)` on `UPDATE` or `DELETE`. Only three kinds of row are mutable: the task row (`lifecycle`, `revision`), job rows (status, progress), and the current personal-settings row, each change of which also appends a history row. Purge (below) is the one explicit delete path.
- **Content-addressed files.** A file is named by the SHA-256 of its bytes and written temp → fsync → rename; the `blob(sha256, size, mime)` row is inserted after the file lands. Uploading the same file twice gives two materials sharing one blob. Derived files (print sheets, OCR crops, corrected photos) are blobs too, with a `derivation(source_sha256, kind, tool@version, params)` row. The server re-hashes a blob before every ERP upload and every print and fails closed on mismatch. Blobs are deleted only by purge, and only when unreferenced; there is no background GC.
- **Pinning rules to a task.** At creation the task references, by content hash, rows of a `rule_set(hash, kind, contract_version, business_version, app_version, content)` table holding the normalized bundled company rules and the project catalog; personal bindings (home city, ERP identity) are copied into the task. A task reads only its pinned content, never the current package, and there is no "upgrade this task" action.
- **Schema migration.** Forward-only kysely migrations run at startup before the HTTP server listens, each preceded by `VACUUM INTO backups/<ts>-<fromVersion>.sqlite` (the last 5 kept). No down migrations. A database newer than the app refuses to start and is left untouched. Migrations change representation only, never the meaning of a business value. Each migration is tested against a fixture database of the prior version.
- **Retention.** Terminal tasks are kept intact; nothing is deleted automatically in v1. A later slice adds an explicit per-task **purge** for terminal tasks: it deletes blobs and business facts and keeps the 审计清单 (audit record) plus an **invoice-identity fingerprint** (a keyed SHA-256 of the normalized invoice identity under a per-install secret), which keeps occupancy without keeping a readable invoice number. Purging a voided task drops its fingerprints, since voiding already released them.
- **Settings surface.** The web page is the only place settings are edited. Changing the home city is a dedicated confirmation showing the old value, the new value and "applies to new tasks only". The ERP password enters the Keychain only through the ERP login flow.
- **Legacy import.**
  - Runs once, at the first startup where `baox.sqlite` does not exist and the legacy directory (`~/.baox`, or `BAOX_HOME`) has `schema.json` `schemaVersion: 1`. It reads the legacy directory without writing to it, runs in one transaction, and records an `import_run` row with counts and outcome. A corrupt file or unexpected schema imports nothing and shows a report; the user retries after fixing, or explicitly chooses to start without the import (recorded). The Chrome profile, runtimes, logs, legacy materials and step tokens are not imported.
  - Imports every identity keyed by `(tenant, account)`; `identity.json` becomes the current binding. Project-book entries carry `number, name, confirmedAt, expiresOn`; `lastCheckedAt` and `lastVerdict` are dropped because the ERP job re-checks the catalog first (ADR-0014). Each home city's `confirmedAt` becomes a settings-history row.
  - Occupancy comes **only** from legacy tasks with a non-empty `erpWriteState`, regardless of status. Legacy `open` and `archived` tasks that never touched ERP release their invoices and are listed as "not migrated" in the report, because the user will re-upload those invoices into the new app. Keys are stored as fingerprints; the new invoice-identity rule ports the legacy `identityKey` derivation with parity tests so the two match.
  - Each ERP-touched legacy task becomes a terminal, read-only task with `origin = legacy`: no materials or candidates, only its occupancy fingerprints, `erpWriteState`, `erpWriteAt`, and the last reconcile bucket and bill number from `erp-attempts.json`. `saved` imports as ERP 草稿已交接 (draft handed over); `upload_dispatched`, `erp-fill` and any other value import as 转人工 (handed off). None can be voided (ADR-0007).

## Considered Options

- **Reuse `~/.baox` with a new layout.** Mixes two formats in one directory and makes a failed import able to damage the only copy of the legacy data.
- **Mutable tables with an audit log beside them.** Two sources of truth that drift; append-only rows make the audit trail the data itself, and ADR-0014 already derives state from facts.
- **Delete business data at the terminal state, keeping only the audit record** (the #15 rule). It would also delete what invoice occupancy needs; the fingerprint keeps occupancy while still dropping readable invoice numbers.
- **Import legacy `open`/`archived` occupancy as ADR-0007 defined it.** It would block the user from re-uploading, into the new app, the very invoices of tasks that are not migrated.
- **Import every ERP-touched legacy task as 转人工**, as the map first said. A `saved` task already passed strict readback; calling it handed off misreports it.

## Consequences

- Supersedes, for the local app, #17's CLI-only settings rule and separate config directory, and #15's deletion of business data at the terminal state.
- Amends ADR-0007: occupancy is held by an open task or an ERP-touched task; `archived` no longer exists, and occupancy survives purge as a fingerprint.
- The `identityKey` derivation is ported from the legacy kernel with parity tests, like the other real-ERP-validated logic.
- Amended by ADR-0018: the legacy import no longer imports identities or the identity binding, and it runs when the first admin account is created, importing everything into that account.
