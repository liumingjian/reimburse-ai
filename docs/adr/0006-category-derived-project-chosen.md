# 费用类别由内核推导，项目归属由用户在任务选择页给出；未验证的费用项目编码硬阻塞

候选明细进 ERP 之前还缺三样东西，它们的来源必须严格分开：

- **费用类别**（住宿 / 本地市内交通 / 外地市内交通 / 长途交通）由内核按票种、
  关联上的参考材料和任务的常驻城市推导。它不是用户的选择题。
- **常驻城市、报销事由、项目归属**材料上根本没有，只能由用户通过本地任务选择 Web
  的**提交动作**给出；用户在对话里说"项目是 111454"不构成任务选择。
- **ERP 费用项目编码**来自一张对照表，表里只放在真实 ERP 上保存过草稿并回读确认过的编码。
  没有这样的样本，编码就是 `null`，对应的明细**硬阻塞**。

外地市内交通就是第三条的现实后果：它在 v1 范围内，但从来没有在真实 ERP 上落过一条明细，
所以它的编码是空的，一旦有明细落到这一类，整批就停下。

## Considered Options

- **让模型判断费用类别**：最省事，也最错。"这趟车算本地还是外地"有确定答案 ——
  行程单上的城市和任务的常驻城市一比就知道。把一件有确定答案的事交给模型，
  等于把确定换成不确定，和 ADR-0003 拒绝让模型转述 PDF 是同一条理由。
- **把费用类别做成任务选择页上的下拉框**：看起来更"尊重用户"，实际是请用户去改一个
  内核已经算得出的结论，还顺带把误选的责任转嫁给他。真正需要用户定的是常驻城市，
  一个字段定完，四类明细的归属同时确定，而且每次结果一样。
- **外地市内交通先借用本地的 `FY008001`**：两者在 ERP 里是不同的费用项目，编码一样就是
  把外地费用挂到了本地项目上。省下的是一次阻塞，赔进去的是一条错的报销记录。
- **让用户在页面上自己填外地市内交通的费用项目编码**：比猜一个好，但内核现在没有
  ERP 项目/费用项目的只读查询，填进来的编码在 ERP 里是否存在无从校验，
  错了要等到保存草稿失败（或更糟，保存成功但挂错）才发现。等 ERP 只读查询那一片做完再说。
- **不推导，把四个类别都留给 ERP 的自动识别**：实测否决。ERP 导入后自动生成的明细
  项目、费用项目、事由一律为空，金额也未必对（save-contract 里三个样本都要人工补齐），
  它给不出这个答案。

## Consequences

- **一个字段定四类归属。** 常驻城市是任务级事实，填一次；每条明细的类别随之确定，
  并且带着可复核的依据（`categoryBasis`，例如"费用发生城市 广州市 不是常驻城市 北京"）。
- **住宿的依据是酒店结账单，不是票种。** 一张增值税专用发票本身不能说明它是住宿费；
  实测去掉结账单后同一张发票就落到 `category_undecidable` 阻塞。这也意味着
  住宿发票必须配结账单才能过这一层 —— 是刻意的，因为入住日期也只有结账单上有。
- **市内交通取不到城市就阻塞，不拿常驻城市顶替。** 顶替等于把"没有证据"偷换成"就在本地"。
- **对照表里三行有编码、一行没有，这件事必须显式可见。** `lines` 的输出里带着整张
  `expenseItemCatalog` 及其 `verified` 标记，免得有人以为四类都能落地。
- **项目号未经核验，并且如实记着。** 选择记录里写死 `projectSource: user_input_unverified`，
  后面的 ERP 层必须自己去对账，不能把它当成已经验证过的主数据。
- **选择绑定的是候选明细本身，不是盘点版本。** 材料没变、但用户重新分摊了一张合并交通票时，
  明细会从一行变成三行，之前"给这一行选了项目"就失效（`task_selection_stale`）。
  实测移除一张票后，两行明细的项目立即回到 `null`。
- **代价：多一个 Web 页面和一次提交。** v1 原本只打算保留任务选择这一个 Web，
  现在实际有三个（确认读数、逐段分摊、任务选择）。三个都是同一条理由：
  需要一次可追溯的提交动作，而对话给不了。
