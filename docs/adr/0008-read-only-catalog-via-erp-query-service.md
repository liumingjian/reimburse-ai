# ERP 主数据用金蝶自带的只读查询服务核对，不去爬选择器的 DOM

费用项目编码和项目号是 baox 往 ERP 里填的两个主数据。在这之前，两者的真实性
都只能靠"我们记的对照表"和"用户填的数字"，内核如实把项目号标成
`user_input_unverified`，等一个真正的核对手段。

核对手段落在 `ExecuteBillQuery` 上——金蝶云星空自带的查询服务，用用户当前
已登录的会话调用。三个决定：

- 用 ERP 自己的查询服务，不打开新增单、不爬弹出选择器的表格。
- 要查的业务对象不是猜的，是从 `ER_ExpReimbursement` 的表单元数据里读出来的：
  `FEXPID -> BD_Expense`、`F_BJYC_PROJECTID -> BJYC_ProJect`。
- 核对结果绑在候选明细的指纹上落进任务工作区，只有"全部通过"才落盘；
  项目号的来源等级据此从 `user_input_unverified` 升到 `erp_catalog_confirmed`。

## Considered Options

- **打开一张费用报销单的新增单，点开项目/费用项目选择器读表格**：这是探查期
  实际走过的路，可行，但它会在 ERP 里创建一个未保存的表单——把"只读核对"
  变成了会留下状态的操作，权限边界从此说不清。而且选择器的元素 ID 带运行时
  UUID，网格分页、列顺序都可能随版本变化，定位器天然不稳。
- **按经验猜业务对象标识**（`BD_EXPENSEITEM`、`ER_ExpenseItem` 之类）：试过，
  全部返回"业务对象不存在"。项目对象还是公司自定义的 `BJYC_ProJect`，
  大小写都不规则，猜是猜不出来的。从元数据里问是唯一可靠的来源。
- **把整个费用项目/项目目录拉下来缓存**：项目目录有大量候选，拉全量既慢又要
  处理分页，还会把大批客户名称落进本地缓存。实际需要的只是"这几个编码在不在、
  这个项目号在不在"，那就只查这些——核对，不是同步。
- **让内核从目录里替用户挑项目**：ADR-0006 已经定过，项目归属是业务决定，
  材料里推不出来。这一层只回答"存不存在、能不能引用"，不回答"该选哪个"。
- **把核对结果记成"这个任务已验证"的一个布尔值**：那样用户在任务选择页上改了
  项目号之后，旧的"已验证"会继续生效。改成按**项目号**索引的一张表，
  换了号自然查不到，也就自然回到未核对——实测确认过这条路径。
- **查询失败时按"没发现问题"放行**：最危险的一种默认。查询失败是"没核对成"，
  不是"核对通过"，一律阻塞。
- **顺手用同一个通道做写入**：不做。这个模块只调 `ExecuteBillQuery` 一个地址，
  这是它敢在"只读"名义下存在的全部理由；写入要走已经定好的浏览器操作路径，
  受保存后置条件约束。

## Consequences

- 核对需要一个身份已 `matched` 的 ERP 会话，和写入侧同一条前置条件。
  会话掉线时是 `not_logged_in`，用户去登录即可（ADR-0002 补记）。
- `catalog` 只证明主数据在 ERP 目录里**存在且可引用**（已审核、未禁用），
  不证明它在费用明细上保存得进去。后者仍然只有保存并回读才算数——
  `FY010002` 因此仍带着 `expense_item_unconfirmed` 提示。
- 项目名称会出现在核对输出里（那正是让用户确认"选的是不是这个项目"的依据），
  但不做全量缓存，落盘的只有本任务用到的那几个号。

> **2026-09-07 修订（#78）。** 「项目号的来源等级据此从 `user_input_unverified` 升到
> `erp_catalog_confirmed`」现在只适用于**没有项目簿来源的旧选择记录**。个人项目簿落成后，
> 选择环节的候选只来自簿中的可选集合，而进簿的前提就是核验过，所以新做的选择一开始就是
> `erp_catalog_confirmed`，不必也不会经过这条升级路径（见 ADR-0006 的 2026-09-07 修订）。
>
> 本 ADR 的其余部分照旧：`ExecuteBillQuery` 仍是核验项目和费用项目的手段——它只是
> 从"选完之后补一次核对"挪到了"录入簿子之前先核一次"，查询失败仍然是"没核对成"而不是
> "核对通过"，费用项目编码这一侧完全没有变化。
