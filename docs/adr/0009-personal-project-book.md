# 项目由员工手工誊录进个人项目簿，录入即硬核验；不内置清单，也不冻结 ERP 快照

用户能选哪些项目，此前有两个候选答案，都不对。已发布的代码是**任务选择页上一个自由文本框**
（`kernel/src/serve.mjs`），用户每次现打项目号，内核明说不校验；未合并的原型分支
`project-picker-prototype-2` 走的是另一头，一份**发布时冻结的 ERP 派生快照**，40 条写死的
`{ code, name }`，原型自己还写了 `ERP_DRIFT` 去模拟快照和 ERP 之间的漂移。前者每次都要重打、
错了没人管；后者要有人维护，而且注定过时。

定下第三条：**个人项目簿**。员工自己从 ERP 里把项目号誊录进来，长期留用；这份簿子是他选择
项目归属的**唯一**来源，选择环节不再提供自由文本框。三个决定：

- **录入即硬核验。** 每次录入都当场做一次主数据只读核对（ADR-0008 的 `verifyProject`）。
  只有 `confirmed` 才进簿；`missing`、`ambiguous`、`unusable` 一律拒绝录入并说明原因。
  因此簿子有一条不变量：**里面每一条在录入那一刻都是 ERP 里真实存在、已审核、未禁用的项目。**
- **项目名称由 ERP 回读写入，用户只填项目号。** 用户手打的名字没有任何权威性，还会和 ERP 错位。
- **选择与维护职责分离。** 报销途中发现簿子里没有想要的项目，不自动添加、不就地新建，
  用户去维护页录入，回来再选。

## Considered Options

- **内置一份发布时冻结的 ERP 项目快照**（原型分支的做法）：它要么由我们维护——那是把一份公司主数据
  抄进代码库，每次项目变动都要发版；要么就慢慢过时，用户看着一个 ERP 里早已禁用的项目却选得中。
  而且不同员工关心的项目只有三五个，把全公司的项目塞给每个人，选择反而更慢。
- **保留任务选择页上的自由文本框**：现状。它的代价不在打字，在于**错误发现得太晚**：
  一个粘错的项目号会一路走到 ERP 写入阶段才报错，而那时发票已经导进 ERP 收票网格
  （`已导入未写明细`），重放导入不可行，一律转人工。用几十毫秒的只读查询换掉一次转人工。
- **录入时不核验，先存下来，用的时候再核**（"机会性核验"）：设计上更宽松，实际是把不变量
  从"簿子里都是好项目"降级成"簿子里有好有坏"，于是每一处读簿子的代码都要重新处理未核验状态，
  选择器还要显示一堆"未核验"的条目让用户自己判断。用户明确否掉了：宁可录入时联网一次。
- **只拒绝 `missing`，`unusable` 和 `ambiguous` 放进去**：那"簿子里全是标准项目"就只成立三分之一。
  已禁用的项目录进来也报不了销，一号对多条时 baox 不替用户挑（ADR-0008），两者都必须在门口挡下。
- **报销途中手打的项目号自动沉淀进簿**：省一次跳转，但它让"加入项目"变成一个用户没有明确发起过的
  副作用，一次手误就会永久留在簿子里反复坑他。选择就是选择，维护就是维护。
- **用 SQLite 存**（用户最初的提议）：这个仓库**零依赖、没有 package.json**，而簿子是几十条、
  单用户、无并发、无查询需求的数据。引入 SQLite 意味着要么抬高 Node 最低版本去用实验期的
  `node:sqlite`，要么添上仓库至今一个都没有的原生依赖。落 `projects.json`，和 `identity.json`
  平级放在数据根下（不是 `~` 下的 dotfile——那和 `kernel/src/paths.mjs` 的平台约定冲突）。
- **给项目做启用/停用开关**：多一个状态、多一处要解释的语义。过期自动隐藏加上用户随时可删，
  已经覆盖了同样的需求。

## Consequences

- **录入项目是一个联网动作。** 硬核验要求一个身份已 `matched` 的 ERP 会话（`authorizedPage()`），
  没登录就录不进去。这是"簿子里全是标准项目"这条不变量的价格，认下来——用户录入的那一刻
  本来就正开着 ERP 在复制粘贴。
- **重试只针对"没问出答案"。** `missing`/`ambiguous`/`unusable` 是 ERP 给出的明确判定，
  不重试，当场拒绝；查询超时、返回非 JSON、CDP 断开才重试，3 次仍失败则本次录入失败。
  没有登录会话既不算失败也不重试，引导用户去登录。
- **`user_input_unverified` 在项目簿这条路径上不再出现。** 从簿子里选出的项目归属恒为
  `erp_catalog_confirmed`。ADR-0006 那条"项目号未经核验，并且如实记着"的后果由本 ADR 取代——
  它描述的是自由文本框那条路径。
- **可选集合实时读，已选归属锁死。** 用户中途去维护页加了个项目，回到任务里立刻能选到；
  反过来他删掉一个项目，不影响已经写进 `selection.json` 的归属——那已经是任务事实了。
  `CONTEXT.md` 里"报销任务创建时固定业务解释"的那句因此把项目簿排除在外。
- **项目失效有两个来源，取并集。** 员工填的过期时间（可空＝永不过期）管"结题了但 ERP 还没禁用"；
  维护页上的"复检全部"用一次 `FNumber in (...)` 批量查询（`verifyExpenseItems` 已有这个写法）
  找出变成 `unusable` 或已消失的项目。两者都只从**选择器**里隐藏，在**维护页**里必须显眼可见——
  看不见就没法清理。**永不自动删除**：删除永远是用户的动作。
  落地时（#79）定死了四件细节：过期**只到日期粒度、按本地日期比较**，用户填的那一天
  当天仍然可选，过了那天才失效——他填的是"结题日"，不是一个时刻；**读不出来的
  `expiresOn` 当作已过期**而不是永不过期，因为簿子可手改，读不懂时让一个来路不明的
  项目继续可选是更坏的那一头；**同一项目号重新录入，本次提交的过期时间覆盖旧值**，
  重录就是把那张表又填了一遍，留空提交就是"我不再给它设结题日了"；**可选集合每次
  现读现算**，连"今天"都现算，跨过零点不用重启就生效。
- **簿子为空是一个独立状态。** 新增 `project_book_empty`（actor 是 user，动作是打开维护页录入），
  和 `project_unassigned`（有得选但还没选）分开——给用户的话术完全不同。
- **交付面收敛，不新开 Web。** 维护页复用 `docs/design/implementation-plan.md` 批次 5 里
  已经规划保留的那个本地项目页（1.0.0 之后只剩重新绑定身份和项目两处本地页）。
  命令面只加只读的 `baox projects` 和弹页的 `baox projects-page`；**增删不做 CLI**——
  有后果的动作要一次可追溯的提交，不走对话，和 ADR-0006 一贯。
- **删除是硬删、无二次确认。** 簿子不是账本，没有审计价值；误删的代价只是重新粘一次项目号，
  而确认弹窗会让"定期清理"变得烦，最后没人清理。
