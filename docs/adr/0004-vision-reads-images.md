# 图片材料由识别 Adapter 读取，读数只作候选

> **状态：已取代（2026-09-11）。** 被[本地报销应用](../design/standalone-app.md)取代：图片路径改为「受管 OCR + 规则，失败转手工补填（手工补填）」，不再有模型视觉（`vision-direct`）及视觉回退；OCR 运行时见 [ADR-0013](0013-managed-local-ocr-for-image-fields.md)。「读数只是候选，须经哈希绑定、内核校验和最终整单确认」这道闸继续有效。继任 ADR 待补。

图片格式的报销材料（发票、行程单、支付水单）由识别 Adapter 读取：默认 `vision-direct` 使用模型自身的视觉能力；明确选择 `ocr-assisted` 时先使用受管本地 OCR，候选不足再交给模型视觉。临时调用任意外部识图工具仍不被接受。

读出来的东西**不是事实，是候选**。它要过三道闸才能成为已解析值：内容哈希绑定 → 内核结构校验 → 用户在最终整单 ERP 明细清单中统一确认。

本决定取代 [ADR-0003](0003-zero-dependency-pdf-text.md) 中「图片一律阻塞、v1 不做 OCR」的部分；文本 PDF 的当前主路径改由 [ADR-0011](0011-markitdown-agent-pdf-candidates.md) 定义，本文只规定图片视觉读取及其确认门。

## Considered Options

- **不做 OCR，要求用户改用 PDF 原件**：ADR-0003 的原方案。实测发现它挡住了真实业务：图片发票是常态，水单和行程单也经常只有截图，而 `fengyun-1.png` 这张**已在 ERP 端到端验证过**的凭证会被挡在门外。用户明确否决。
- **接入系统 OCR（macOS Vision）**：本地、确定性、不经过模型，技术上最"干净"。实测这台开发机上 `swiftc` 可用，但那是因为它装了 Xcode 命令行工具 —— 普通同事的电脑上没有。这等于把 ADR-0002 好不容易消掉的安装负担又搬回来。用户明确否决。
- **云端 OCR 服务**：要把发票原件发到外部服务，超出 v1 的隐私边界。
- **临时调用本地 OCR 模型（tesseract / PaddleOCR）**：未经版本、资产和运行时管理的临时工具会破坏可复核性；需要 OCR 时只能走 ADR-0013 定义的受管 `ocr-assisted` Adapter。

## Consequences

- **模型第一次进入了事实链，因此必须把它限定在"抄写员"的位置。** 设计共识里"模型输出不构成业务事实"这条不变，但需要说清它到底禁的是什么：禁的是模型**判断、推算、补全**；不禁模型**读一份在册材料上印着的字**。区别在于前者无来源，后者的来源是材料本身，而且可复核 —— 用户拿着原图就能核对。
- **读数绑定内容哈希。** 提交读数必须带上材料的内容哈希，内核重新计算后比对。这带来一个关键性质：**图片一改，之前的读取和确认自动失效**（实测：追加一个字节即落到 `reading_stale`）。确认永远只对某一串确定的字节有效。
- **结构校验是模型控制不了的算术。** 20 位发票号码、合法日期、金额守恒（不含税 + 税额 = 价税合计，按分精确）、闭集票据类型、白名单字段。编出来的数字凑不平守恒式，这是最硬的一道闸。
- **提示词里必须给"看不清"留一条体面的出路。** 这是整套设计里最容易被忽略、也最要命的一处：如果读不出来会被追问或视为失败，模型就有动机去猜。因此 Skill 明确写着：看不清写进 `unreadable` 是完全正当的答案；**猜一个值比说看不清严重得多**；金额守恒不通过是正常结果，不是你的失败，凑数字是这一整套设计里最严重的错误。
- **最终裁决权在用户，通道是最终整单明细表而不是逐张图片确认。** 表中列出发票/材料、票种、三项金额、费用起止日期、城市、出发点、目的地、费用类别、费用项目和材料关联，用户对照原件一次性核对。对话里说"没问题"不算确认。
- **代价：候选会先继续流转。** 图片和 PDF 都允许在没有重大歧义时先进入分类、关联和费用事件，用户只在所有可填 ERP 信息汇总后确认；多页发票仍在 V1 入口阻塞并要求排除或替换。
- **ERP 发票助手的识别结果不作为来源。** 那是平台自己的系统，不是 baox 的证据链；而且依赖它会把重复检查推到上传之后，与契约的顺序冲突。

## 补记（2026-09-07，真机试用：模型跳过了"看"这一步）

- **"我看不到图片"必须被明确排除在合法答案之外。** 真机试用里模型跑完 `ocr-request` 拿到工单，**一次 `Read` 都没调用**，就回报"当前图片内容没有成功显示给我"，并让用户去检查、重新导出图片——而那两张图（1816×1396 的 PNG）完全正常。这是上面那条「给『看不清』留一条体面的出路」的副作用：出路留得太宽，宽到可以不看就走。
  修正的是边界而不是那条出路本身：`unreadable` 指的是**正看着的图上认不出某个字段**，从来不指没看；只有真正调用过 `Read` 并且**它返回了错误**，才能报"这张图读不了"，而且要原样引用那条错误。工单 JSON 里也加了一条 `next`，把"逐个 `Read` 打开 `items[].absPath`"写成内核输出的一部分，而不是只躺在参考文档里。

## 补记（2026-09-07，纠正与争议：确认通道改到终端，用户改的值不直接落库）

- **「最终裁决权在用户，通道是本地页面而不是对话」这一条里，通道变了，裁决权没变。** 1.0.0
  把逐份确认从本地确认页搬到**终端定宽表格**（`confirm_table`）：内核渲染好整块文本，
  用户当面表态，模型带着一次性凭据回传。变的是界面，不变的是「确认由一次带凭据的往返构成」——
  聊天里飘过的一句"对的"仍然不构成确认，因为它不带凭据，内核看不见它。本地页面收窄到
  重新绑定身份和浏览项目目录两处（见 ADR-0002 的对应补记）。
- **用户在那张表上说的值，也不是事实。** 这是这一条最容易被读反的地方：把裁决权交给用户，
  不等于把用户口述的数字直接写进读数。两边都可能错 —— 模型可能看模糊了认错，用户也可能看错。
  所以指错的处置是**开一场争议**（`reading_disputed`）而不是改一个值：内核摆出证据链
  （材料绝对路径、机器读到的原文、模型当时的清晰度判断），派一个干净上下文的子 Agent
  只重读那一个字段，再把三份说法一起摆给用户拍板。用户拍板之后读数**仍然停在未确认**，
  还要在整张表上过最后一次目。
- **守恒式在这里也不让路。** 用户的改动打破「不含税 + 税额 = 价税合计」时，内核算出差额、
  说清不平在哪里，然后停下。它**绝不反算另外两个值** —— 反算出来的那个数看起来最像对的，
  实际上会是整条链子上唯一一个没有任何人读过的值。补不上就整条读数退回待办，等用户换一份
  看得清的原件。
- **每个字段从此带来源**：`vision`（模型抄的）/ `user`（用户对着原件给的）/ `kernel`
  （内核从 PDF 文字层解出来的）。一份读数里同时有前两种是常态，而"这个数是谁说的"
  是后面每一次复核唯一要问的问题。

## 补记（2026-09-07，第二轮真机 QA：模型看不见图，于是去找识图工具）

这一轮 QA 跑这套流程的不是 Claude，是另一个模型。它**按规矩逐张调了 `Read`**，
`Read` 也确实把两张 PNG（310KB / 87KB）交了回去 —— 然后它转头去敲 `file`、`mdls -name pixelWidth`、
`which tesseract`、`swift --version`，挨个探 `cv2` / `easyocr` / `paddleocr` / `ocrmac` / `Vision`，
最后按文件名和尺寸推断出 `docType`，把所有字段填进 `unreadable` 交了上来。内核收下了它。
用户看到的是一张什么都没有的确认表。

补记的是两条边界，一条比一条硬：

- **「看过的凭据」不能是元数据答得出来的东西。** `sighted.shape` 是从宽高比里选一个档位，
  而宽高 `mdls` 一条命令就报得出来 —— 于是这道凭据在一个看不见图的模型面前一次就过了。
  它拦得住"懒得看"，拦不住"看不见"。内核这一侧没有解码器，出不了真正基于画面内容的题
  （PNG 靠 zlib 还能解，JPEG 不行，而两种格式都得支持），所以**不去把这道题出得更难**，
  改为在结果那一侧收口。
- **一份一个字段都没有的读数不是读数。** 这一条和"看不清是正当答案"不冲突，两者说的不是
  一件事：`unreadable` 指的是**正看着的那张图上的某个字段**认不出，而整张图上一个字段都认不出，
  说的是这张图没有被看见 —— 何况内核刚刚量出它的尺寸，图是完好的。这道闸比凭据难绕得多：
  票面上的字只有看见了才抄得出来。
  处置是分级的：第一次驳回，附上"外部识图工具不算数、看不见就照实说"；连着两次
  （`MAX_EMPTY_READINGS`）就不再派工单，转成一条摆给用户的开放项 `vision_unavailable`
  —— 换一个看得见图的模型，或者换一份 PDF 原件。**给"看不清"留的那条出路仍在**，
  它只是从"悄悄记成一份空读数"变成了"当着用户的面说出来"。
- **禁用外部识图工具，写进内核的输出里。** `tesseract`、`mdls`、`sips`、macOS Vision、
  `easyocr` 之类读出来的东西内核一律不收。这条原先只写在 `references/image-reading.md` 里，
  而 QA 那一轮模型读了那份文件仍然去找工具了 —— 所以它现在也是 `read_images` 那一步 JSON
  的一部分（`onlyYourOwnEyes` / `ifYouCannotSeeImages`）：**模型看得见的才算数。**
  理由不在工具好坏，而在证据链：中间插进一个外部程序，用户就再也无法只凭原图核对抄下来的东西。

## 补记（2026-09-10，Adapter 和整单确认边界）

- 默认图片路径是 `vision-direct`，因为当前模型视觉准确度优于现有 OCR；`ocr-assisted` 作为可切换的受管适配器保留，先 OCR、再对不足候选使用模型视觉。
- 发票业务字段只需要不含税金额、税额和价税合计。发票号码仅作为隐藏技术身份用于重复检查；开票日期、开票方、购买方和项目名称不进入最终 ERP 明细，也不再是阻塞条件。
- OCR 与模型视觉的结果都只是候选。图片和 PDF 都继续向分类与费用事件流转，最后用一张整单明细表确认；该表必须覆盖发票/材料、三项金额、起止日期、城市、起点、终点、费用类别、费用项目和材料关联。
- V1 不支持多页发票。内核识别到主要凭证对应多个 PDF 页面时，形成阻塞项，明确要求用户排除或替换。
