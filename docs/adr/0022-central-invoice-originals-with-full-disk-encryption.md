# Invoice originals stay central, protected by full-disk encryption rather than an envelope

Once the server runs on Linux and serves several people, the invoice originals (PDFs and images) need a home and a protection model. Decided in [#226](https://github.com/liumingjian/reimburse-ai/issues/226); it builds on ADR-0018's ownership model.

## Decisions

- **Originals are stored centrally**, reachable only through their owner's tasks.
- **Protection is full-disk (or partition) encryption plus encrypted backups**, combined with owner-scoped authorisation on every read path.
- **No application-level envelope encryption.** No per-file data keys, no master key held by the service.
- A retention and cleanup policy after a reimbursement completes is a sensible later addition on top of this, not a substitute for it.

## Considered Options

- **Keep no originals: store only OCR results and hashes, and have the extension read files from the user's disk at fill time.** Rejected. It sounds best for privacy but removes half the product: 去打印 (go to print) composes the originals into a printable document, and the parsers re-read them whenever a field candidate has to be re-derived. (An earlier draft of this sentence cited 收票单号 (receipt number) read-back as the second reason. That was wrong: 收票单号 is generated by the ERP at import and appears on no invoice, so the read-back's expected value comes from the ERP receipt grid, never from the originals.) It also loses everything when a user changes machines.
- **Per-file data keys under a master key (envelope encryption).** Rejected. The server *must* read plaintext to run OCR, compose print output and verify readback, so the master key would live in the service process and the decrypt path would run constantly. It does not defend against "the application is compromised"; it defends against "someone walks off with the disk", which full-disk encryption already covers. In this threat model it is paper benefit and real complexity.

## Consequences

- Every read path for originals carries an owner check.
- Deployment documentation must specify an encrypted volume and encrypted backups; the protection is operational, so a misconfigured deployment silently loses it.
- Content-addressed blob deduplication stays as ADR-0018 requires: blobs may be shared on disk but are reachable only through the owner's tasks.

## Deployment deviation, phase 1 (2026-09-21)

The decision stands; the first deployment does not meet it, knowingly. The intranet host chosen for the
browser-extension V1 round (`10.250.0.222`, probed 2026-09-21) carries **no encrypted volume** — plain LVM
on xfs, no dm-crypt — and has **no backups** at all, encrypted or otherwise. Invoice originals will rest
unencrypted there.

Two things make this affordable for now and not later: the instance starts from an empty database with no
real 报销任务 (reimbursement task) in it, and it is reachable only over the company VPN. Neither will hold
once employees file real invoices on it.

The honest reason is sequencing, not a revised threat model: the core flow comes first. A keyfile-unlocked
LUKS volume was considered and is not a fix — the key would sit on the same unencrypted disk, which is
exactly the "someone walks off with the disk" threat this ADR names. Real protection needs a passphrase at
boot or an external key, and that is its own round.

This deviation must be closed before the instance holds real reimbursements.
