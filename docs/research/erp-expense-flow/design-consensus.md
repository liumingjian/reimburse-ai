# baox v1 生成 Spec 前的设计总共识

状态：设计共识已确认；本文不是实现 Spec。  
范围：基于 #8、#25 以及后续材料整理、重复检查和 ERP 验证讨论形成。  
目标：在生成实现 Spec 前，固定产品边界、状态契约和放行条件，并把尚未验证的外部事实单独列出。

## 一、产品边界

- baox 是本地优先的报销材料整理和 ERP 草稿交接工具。一个输入目录对应一个`报销任务`。
- 用户入口是 Claude Code Agent Skill，不是员工直接使用的命令行工具；材料盘点、判重、金额守恒、确定性校验、动作账本和 ERP 对账仍由确定性内核执行，Skill 不判定、不裁决放行、不操作浏览器。见 ADR-0001。
- v1 只保留一个 Web 界面：任务选择。材料整理确认在对话中完成。
- v1 只处理四类费用：住宿、本地市内交通、外地市内交通、长途交通。
- v1 只接受 PDF、PNG、JPG。OFD、压缩包、邮件、表格、其他格式以及一个文件中混有多个材料，均不能静默跳过，必须形成阻塞问题。
- v1 内置唯一 ERP 入口为 `http://erp.antute.com.cn/k3cloud/html5/index.aspx`；用户不需要在初始化、任务或 Web 中输入 ERP 地址，也不能自由替换入口。
- 一个任务可以混合上述四类费用，但必须属于同一员工、同一收款人和同一报销事项。不同主体或事项必须由用户拆成不同任务；系统不自动拆目录。
- 原始输入目录永远不被移动、重命名、覆盖或删除。整理是语义整理和派生材料生成，不是改造源目录。
- 不支持采购、餐饮、停车、燃油、路桥、充电、机票、普通商品或服务发票、红字/冲红等超出 v1 范围的场景。

## 二、任务工作区与生命周期

每个任务都在用户级持久化数据目录下拥有独立工作区。推荐使用操作系统标准的应用数据根目录，例如 macOS 的 `~/Library/Application Support/baox`、Windows 的 `%LOCALAPPDATA%\\baox`，再按 `tasks/YYYY-MM-DD/<task-id>/` 组织。日期用于查找，`task-id` 才是身份。

工作区至少保留以下逻辑内容：

- 本次材料盘点及其版本；
- 原始文件的不可变快照信息和整理后的材料副本；
- 解析记录、字段候选、费用事件、候选明细和证据关联；
- 待确认项、重复检查、金额检查和动作账本；
- ERP 上传副本、上传清单、回读结果和 ERP 就绪快照；
- 面向用户的脱敏整理报告和机器可读状态。

任务在中断、恢复、ERP 状态未知、转人工或 ERP 草稿交接后都保留。系统不自动删除，也不自动云端备份。用户若明确清理，必须走受支持的清理流程；`ERP 写入结果未知`的任务不可清理。v1 依赖操作系统用户权限和磁盘加密，不另行承诺应用层加密。

建议的状态主线为：

```text
材料盘点
  -> 材料整理中 / 待确认
  -> 材料整理确认
  -> 任务选择 Web
  -> ERP 就绪快照
  -> ERP 自动化中
  -> ERP 草稿已交接
```

任何阶段都可能进入`转人工`或`ERP 写入结果未知`。未知结果不得通过重放上传来“试试看”；必须先做只读对账，无法唯一判断时转人工。进入`ERP 草稿已交接`后，baox 不再追踪用户是否检查、提交、审核或付款。

## 三、材料与证据契约

每个文件先变成一条有稳定`材料标识`的材料记录。记录至少区分：原始格式、按内容识别的 MIME、原文件路径、SHA-256、材料角色、解析版本和来源任务。扩展名只能作为提示，不能作为格式事实。

材料角色只有以下业务结果：

- `主要报销凭证`：允许进入 ERP 上传清单的发票或客运凭证；
- `参考材料`：水单、行程单等用于证明费用事实但不上传的材料；
- 范围外或无法确定角色的材料：必须阻塞，不能静默忽略。

`发票身份`、票面金额、税额、开票日期和`发票票种`属于法定或票面事实，必须由材料证据或可靠解析结果支持。用户可以选择字段候选、修正材料角色和证据关联、补充或替换源材料、排除费用事件，以及为没有逐段金额的合并交通票提供逐段价税合计；不能用自由输入强行改写缺少证据的法定事实。

一个`费用事件`代表现实中的一次费用：交通通常按一个可辨识的行程段，连续住宿通常按一次连续入住，火车票通常按一张票。一个事件投影为一个`候选明细`，一个事件恰好有一个主要报销凭证；参考材料可以为零个或多个，且同一参考材料可以支持多个事件。材料和事件通过证据关联连接，不把文件机械地两两配对。

参考材料不是按费用类别强制要求的附件。主要凭证已经直接证明所需事实时，可以没有水单或行程单；主要凭证缺少必需事实且没有可接受参考材料时，形成阻塞性的`待确认项`。

## 四、整理产物和确认顺序

一次运行必须先建立有版本的材料盘点，再生成可追溯的整理产物。至少要能回答：有哪些文件、每个文件是什么角色、哪些字段来自哪里、形成了哪些费用事件和候选明细、哪些材料被排除、哪些问题仍未解决、哪些发票将上传以及金额是否守恒。

用户确认分成两个边界清晰的动作：

1. `材料整理确认`：用户在与 Skill 的对话中查看摘要和问题清单，处理材料角色、候选选择、证据关联、补充/替换材料、排除事件和合并交通分摊等问题；v1 不为此提供 Web 界面。
2. `任务选择`：在本地 Web 工作台中为候选明细选择 ERP 项目，可逐行选择，也可对明确选中的多行批量应用同一项目；确认由该界面的提交行为构成，用户在对话中的口头表述不构成任务选择。

材料仍有问题时不能打开项目选择 Web，也不能启动 ERP。已经被材料明确证明的事实不要求用户逐字段重复录入。材料、规则、项目目录或任务选择发生变化时，旧的 ERP 就绪快照立即失效，必须全量复检并生成新快照；旧项目选择只能在重新验证后保留，不能自动替换成新项目。

`111454`只是本次交通验证使用的项目号，`广州`只是本次交通验证使用的常驻城市。二者都不是产品默认，也不能自动套用到住宿或铁路。正式任务必须由用户在项目选择 Web 中选择项目。

## 五、重复发票与放行门禁

重复检查必须在自动整理完成后、项目选择 Web 和 ERP 上传之前完成，并且在每次材料变更后重做。检查对象是主要报销凭证，不是全部 PDF 文件。

重复事实分为三层：

- 当前任务内，按对应票种的发票身份判定同一法定发票；
- 当前账号或 ERP/发票助手中已经存在的外部记录；
- baox 历史任务中已经保存 ERP 草稿或明确标记为已使用的同一发票身份。

文件 SHA-256 相同是文件完全相同的强证据，但文件名、金额、日期相同，或共享同一行程单/水单，都不能单独证明法定发票重复。参考材料不作为主要发票参与重复判定。

存在明确重复、身份不完整、候选冲突或外部状态未知时，任务必须阻塞。用户不能点击“确认继续”绕过重复；只能排除/替换材料、把误分类材料改为参考材料、修正有证据支持的发票身份，或明确转人工。外部重复只有在重新查询确认已消除后才能解除；查询能力不存在或结果未知时继续阻塞。

唯一放行条件是：所有材料均已处置，`待确认项 = 0`、`重复发票 = 0`、确定性校验错误 = 0，且每个纳入的候选明细都有完整证据关联和金额守恒结果。自动整理结束后发现重复时，必须先在进入 Web 前提醒用户并持续阻塞，直到问题真正消除。

## 六、ERP 上传、导入与保存

- 用户只需完成一次会话授权：Skill 引导用户以远程调试方式启动自己的 Chrome，由用户自行登录 ERP，内核随后独占接管该浏览器。用户声明「已授权」不成立授权，内核必须先只读探测登录状态，并确认登录身份与本任务的员工身份一致；不一致时硬阻塞。正常路径不要求用户逐张选择或上传发票，baox 通过受控浏览器自动化执行文件选择、识别、导入和保存。见 ADR-0002。
- 只有主要报销凭证进入上传清单；水单、行程单等参考材料留在本地证据链中。
- 同一张合并交通发票只上传一次、形成或复用一条收票记录；它可以支持多个行程段和多个 ERP 明细。
- 每次上传和导入都必须记录意图、派发、候选数量、唯一匹配、收票回读、明细回读和保存后置条件。按钮点击成功不等于上传成功，上传成功不等于可保存。
- 导入后必须独立核对收票行、费用明细行、项目、费用项目、事由、发票类型、不含税金额、税额和价税合计。任一回读与 ERP 就绪快照不一致都停止并形成待确认项。
- v1 的 ERP 权限上限是保存草稿。禁止自动提交、审核、下推、付款、解绑、删除或改变外部既有记录。
- 一个报销任务产生一个 ERP 草稿；是否能在一个 ERP 单据中容纳多类别、多项目明细，必须用真实 ERP 样本验证，不能从单票成功推断。

合并交通发票的分摊规则是确定性的：有票面逐段金额时直接使用；没有逐段金额时，用户必须直接提供每段税价合计。系统只按固定金额和税额规则计算并分别检查不含税、税额和价税合计守恒。不得由模型平均、按比例、按距离、按时长或编造金额；缺少逐段金额形成 `allocation_required` 阻塞。

## 七、必须验证的事实

以下不是需要用户再次猜测或承诺的设计问题，而是生成可执行 Spec 和正式发布门槛前必须由 baox 通过样本、ERP 只读观察或厂商资料验证的事实：

- 每种允许票种的发票身份字段、身份完整性规则、票种识别和解析失败行为；
- PNG/JPG 的端到端解析、证据定位和 ERP 上传/导入/回读；当前图片只完成静态角色核验，不能据此宣称图片链路已支持；
- 住宿普通发票、允许范围内各类客运凭证、真实合并交通发票的多事件/多明细映射；
- 含正负项目行的交通发票在发票助手、收票记录和费用明细中的金额语义；
- ERP 外部重复记录是否存在稳定、可查询、可对账的只读能力；若没有，产品必须保持阻塞或转人工；
- 唯一默认 ERP 地址当前使用 HTTP；必须确认登录和自动化写入的安全传输方案，否则只能支持人工探索，不能作为正式自动化发布入口；
- ERP 对多类别、多项目单据的行级保存能力、保存后唯一对账信号，以及中断恢复时的状态判定；
- 上传入口、识别等待、导入和回读的稳定自动化契约，以及 ERP 页面版本漂移的检测；
- 可隔离、可重置的测试身份或测试租户。个人账号只能用于受控的保存级探索，不能作为正式发布证明；
- 用户级工作区的权限、显式清理、备份责任和工作区丢失后的恢复规则。

在这些事实未验证前，系统可以承诺保守整理、证据追踪和遇到未知即阻塞，但不能承诺所有允许票种都能自动写入 ERP。

## 八、生成 Spec 的入口条件

生成实现 Spec 前，需要满足四个条件：

1. 本文的设计决定保持不变，并同步到领域词汇表；
2. “必须验证的事实”逐项有证据、样本或明确的阻塞行为；
3. 验收语料覆盖四类费用、三种文件格式、重复/冲突/缺失/金额不守恒/中断恢复等关键状态；
4. Spec 对每个失败状态都定义用户可见提示、允许的纠正动作、重新检查条件和是否转人工。

达到入口条件后，Spec 才能把本共识展开为数据结构、命令、Web 状态、ERP 适配器、测试矩阵和验收标准。任何未验证的 ERP 行为都必须以“阻塞/转人工”写入 Spec，而不是以乐观的自动化路径代替。
