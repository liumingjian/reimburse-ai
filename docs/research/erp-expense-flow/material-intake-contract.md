# 材料盘点与 ERP 就绪契约

设计日期：2026-09-04

## 结论

一个杂乱目录不能直接视为“待上传发票目录”。baox 必须先建立一次有版本的`材料盘点`，把每个文件变成可追溯的材料记录，再完成材料角色、发票身份、费用事件、字段候选、材料证据关联、重复检查和确定性校验。只有用户完成`材料整理确认`，并在本地任务选择 Web 中确认项目归属等业务选择后，才能生成`ERP 就绪快照`并进入 ERP Web。

这里的 ERP Web 是执行面：它按已锁定的快照选择 ERP 主数据、上传纯发票、导入收票、填写明细和保存草稿。项目归属的业务决定不应被推迟到 ERP Web，也不应由票面金额、文件名或项目选择器的第一项自动推断。

## “文件编码”的四个概念

“文件编码”容易把四类不同事实混在一起。契约将它们分开：

| 概念 | 用途 | 规则 |
| --- | --- | --- |
| 原文件格式 | 决定能否解析和能否交给 ERP 上传 | v1 只接受 PDF、PNG、JPG；通过文件内容和 MIME 识别，扩展名只作提示。OFD、压缩包、邮件、表格和其他不支持格式形成待确认项，不能静默跳过。 |
| 材料标识 | 在当前报销任务中稳定引用一份材料 | 系统为材料盘点中的每个文件建立稳定标识；文件名只用于展示，不能作为业务主键，也不改写用户原文件。 |
| 内容哈希 | 发现完全相同的文件副本和检测文件是否被替换 | 对原始二进制内容计算 SHA-256。相同哈希是强的“文件完全相同”证据，但不是所有场景下的法定重复发票证明。 |
| 发票身份 | 判断法定发票是否重复 | 按发票票种提取对应的身份字段；它与内容哈希、金额和材料标识分开保存。参考材料通常没有发票身份。 |

文件名和路径按 UTF-8 作为展示文本保存；原文件字节不重新编码。系统在操作系统标准的用户级持久数据根目录下为每个报销任务创建独立的任务工作区，把材料快照、生成的整理产物、派生件和纯发票上传副本放入其中，不改动原目录。为浏览器上传生成的动作只引用已核验的工作区文件路径，日志不持久化原目录绝对路径、Cookie、token 或短期 URL。

## 目录进入系统

`baox run <目录>` 的第一步不是 OCR，而是固定材料盘点：

1. 在指定根目录内递归枚举文件，保留相对路径；不越出根目录，也不把目录名、文件名当作票种或业务归属。
2. 对每个普通文件记录材料标识、相对路径、原始扩展名、检测格式、字节大小、内容哈希和读取状态；空文件、损坏文件、无法识别格式的文件都不能被隐式忽略。
3. 按稳定顺序处理材料，生成一个材料盘点版本。源文件保持不变，整理结果写入任务自己的事实存储。
4. 目录中的文件新增、删除或内容哈希变化时，形成新的材料盘点版本；旧的 ERP 就绪快照立即失效，不能拿旧快照继续上传。
5. 在用户级持久数据根目录下创建本任务专属工作区，按任务创建日期和唯一任务标识组织子目录，使用材料标识生成稳定的内部文件名；工作区只放本次任务的材料快照、整理副本、派生件、机器可读清单、上传清单、报告和状态事实。
6. 任务工作区在任务中断、恢复、ERP 写入结果未知、ERP 草稿已交接或转人工后均保留，不自动清理；用户若明确删除，必须通过受支持的任务数据清理流程。工作区丢失时，只能在 ERP 写入前基于原目录重新校验并物化；ERP 动作开始后不得因工作区丢失而重新上传或重放。
7. 用户补充或替换材料时，只能修改原始材料目录并通过 `baox resume` 或新一次 `baox run` 重新盘点；本地 Web 不提供文件上传，也不直接改写任务工作区。新材料盘点版本形成后，旧版本的 ERP 就绪快照不可继续使用。

## 重复运行与历史材料

同一材料目录再次运行时，先判断是否存在内容相同且尚未结束的报销任务；存在时引导用户恢复原任务，不创建第二个任务。原任务已经交接或结束时，新的运行可以创建新的报销任务，但必须继续检查历史任务中的发票身份。

跨任务历史中已经保存 ERP 草稿或被明确标记为已使用的发票身份，会对新任务形成阻塞性的`待确认项`。历史任务中被用户排除、从未进入 ERP 或尚未完成的材料只形成可追溯提示，不直接判定为重复；历史结果不明确时保持阻塞。

材料盘点版本变化后，旧解析记录、确认和项目选择保留为历史事实。未受影响的候选明细可以在全量复检后继续采用原任务选择；受影响的材料关联、费用事件和候选明细必须重新解析，新产生的候选明细不得继承旧项目选择。

当前 v1 的上传目录只包含被判定为`纯发票`的主要报销凭证。水单、行程单、酒店结算单和其他佐证材料保留在材料盘点中，但只作为`参考材料`参与证据关联，不进入 ERP 发票上传入口。

## 提取结果放在哪里

提取结果不直接写入 ERP，也不只留在模型上下文中，而是分层保存在报销任务内：

| 层 | 保存内容 | 是否可直接作为 ERP 值 |
| --- | --- | --- |
| 材料盘点 | 每个文件的材料标识、来源、哈希、格式、角色和解析状态 | 否 |
| 字段候选 | 材料原文片段、规范化建议、材料证据状态和来源材料标识 | 否；需要规则确定或用户选择 |
| 解析记录 | 确定性规则或用户对候选的选择、纠正、补录和理由 | 是确定已解析值的依据 |
| 已解析值 | 当前任务采用的票种、身份、日期、金额、税额、城市、起终点等权威事实 | 可以投影到候选明细 |
| 费用事件与候选明细 | 一笔现实费用及其 ERP 明细候选；包含材料证据关联和金额守恒结果 | 项目归属等任务选择完成后，才可进入 ERP 就绪 |
| 待确认项 | 缺失、歧义、冲突、重复、范围外材料和校验失败 | 有一项未解决就不能放行 |
| ERP 上传清单 | 只含主要报销凭证的材料标识、已核验工作区文件路径、预期发票身份和金额 | 只用于上传，不替代已解析值 |
| ERP 就绪快照 | 材料盘点版本、已解析值、候选明细、任务选择、规则版本和放行检查结果 | ERP 自动化唯一允许使用的输入 |

发票身份等敏感事实可以用于任务内重复检查，但界面和审计清单应按脱敏规则展示。ERP 回读的收票记录、明细回读和保存结果属于 ERP 动作尝试的外部证据，不反向改写原始材料事实。

## 自动整理必须产出的材料

在打开项目归属界面前，系统至少要准备并能展示以下内容：

- 材料盘点版本，以及全部文件的处置结果：主要报销凭证、参考材料、范围外材料或待确认材料。
- 每一张主要报销凭证的票种、发票身份、开票日期、不含税金额、税额、价税合计和解析证据。
- 每一份参考材料支持哪些费用事件；不能只因金额相同就把材料配成一组。
- 费用事件和候选明细数量；一张合并交通发票的多段行程必须保留可辨识的行程段边界。
- 每条候选明细的日期、城市、起点、终点、费用类别、金额、税额和证据关联；不能确定的字段标为 `ambiguous` 或 `missing`。
- 当前任务内重复检查、外部既有发票记录检查及其不确定性结果。外部记录无法查询时，状态是阻塞性的未知，不是“没有重复”。
- 金额守恒、票种到 ERP 发票类型映射、日期和城市规则等确定性校验。
- 仅由主要报销凭证组成的 ERP 上传清单；参考材料不能混入清单。
- 任务选择所需的固定事实和主数据来源，例如员工身份、公司规则、项目目录、常驻城市和默认部门。当前交通验证样本使用常驻城市广州和测试项目 `111454`；这只是本次 ERP 验证的输入，不是产品默认。正式报销任务中，用户仍须在本地任务选择 Web 中为候选明细选择项目，交通样本中的测试项目不能自动套用到住宿或铁路费用。

推荐的整体放行条件是：所有材料均已处置，`待确认项 = 0`、`重复发票 = 0`、确定性校验错误 = 0，且所有候选明细都有完整的材料证据关联和金额守恒结果。

## 费用事件与证据关联

一个报销任务可以同时包含 v1 允许的住宿、铁路和市内或跨城客运费用，前提是员工、收款人和报销事项一致。每条候选明细仍须单独完成项目归属；测试样本使用的项目号不构成生产默认。

交通费用按可辨识的独立行程段形成费用事件和候选明细；连续住宿通常形成一个费用事件；一张铁路客票通常形成一个费用事件。每个纳入的费用事件恰好有一份主要报销凭证，可以有零份或多份参考材料；同一份参考材料可以支持多个费用事件，材料之间不直接建立配对关系。

一张合并交通发票可以作为多个费用事件的共同主要凭证，但只能上传一次。各候选明细的分摊金额必须分别守恒到同一张发票的总不含税金额、税额和价税合计。

参考材料不是按费用类别强制要求的附件。主要报销凭证已经直接证明候选明细所需事实时，费用事件可以没有参考材料；主要凭证缺少必需事实且没有可接受的参考材料时，形成阻塞性的`待确认项`。

如果合并交通发票没有逐段金额，用户必须直接提供每段价税合计；系统只按固定金额和税额规则计算并检查总额守恒。用户没有提供逐段金额时，Agent 不自行平均、按比例、按距离、按时长或让模型编造，生成 blocking `allocation_required`。

一个报销任务最终形成一张 ERP 草稿；住宿、铁路、交通和多个项目的候选明细都作为同一张单据的明细行。不同员工、收款人或报销事项必须在材料盘点前后拆成不同报销任务。

## 用户确认与两个 Web 边界

用户需要确认，但不应被迫逐字段重复录入已经由材料明确证明的事实。确认分为两个不同动作：

1. `材料整理确认`：用户查看材料摘要和问题清单；对歧义材料选择角色、接受或拒绝证据关联、补充或替换材料、排除重复或范围外材料，并确认全量检查已归零。存在问题时可以打开“整理纠正 Web”，但这个界面不能选择项目归属，也不能启动 ERP。
2. `任务选择确认`：只有材料整理确认通过后，才打开本地任务选择 Web。用户在这里确认常驻城市、项目归属和其他材料无法证明的业务事实；同一规则明确覆盖的多条交通明细可以批量应用，但必须有一次可追溯的确认。项目选择提交后，系统重新检查并锁定 ERP 就绪快照。

材料整理确认不允许任意改写法定发票事实。用户可以选择字段候选、修正材料角色和证据关联、提供合并交通票的逐段价税合计、补充或替换原始材料，或排除费用事件；发票身份、票面金额、税额、开票日期和票种在缺少材料证据时不能通过自由输入强行放行。

ERP 自动化授权是第三个独立事实：用户允许 baox 使用已登录的 ERP 浏览器会话。它不等于材料确认，也不等于项目选择确认。

推荐的状态顺序是：

```text
杂乱目录
  -> 材料盘点版本
  -> 自动分类与事实提取
  -> 费用事件 / 证据关联 / 候选明细
  -> 重复与确定性检查
  -> 材料整理确认
  -> 本地任务选择 Web：项目归属与其他业务选择
  -> 全量复检并锁定 ERP 就绪快照
  -> ERP 授权
  -> 自动上传 / 导入 / 映射 / 保存
  -> ERP 只读回读与草稿交接
```

任何材料、规则或任务选择发生变化，都必须回到全量复检并生成新快照；不能让已打开的旧 Web 页面继续提交旧版本选择。项目目录更新后保留历史选择，但必须按新目录和 ERP 当前主数据重新精确验证；不能自动替换项目。

任务工作区同时保留机器可读事实和用户可查看的整理报告。报告至少包含材料处置、费用事件、候选明细、证据关联、重复检查、金额校验和 ERP 上传清单的脱敏摘要；本地 Web 读取结构化事实，不能以报告文本反向驱动业务状态。

## 上传与回读

进入 ERP 后，系统从 ERP 上传清单逐张派发已核验文件；用户不需要逐张选择，但仍需要一次会话授权。每一次上传和导入都要记录动作意图、材料标识、候选识别结果、ERP 收票/明细回读和金额守恒结果。

导入后必须重新读取 ERP 明细。当前实测表明，ERP 可能把价税合计写入费用金额、把税额置零、保留默认发票类型并留下空的项目字段；因此上传成功不是整理成功，导入成功也不是可以保存。任一回读与 ERP 就绪快照不一致，都要停止并形成待确认项。

保存草稿还必须同时满足保存契约中的后置条件：单据编号生成、页签进入“修改”、收票行和明细行数量正确、金额守恒，并且没有提交、审核、下推、付款、解绑或删除动作。

用户级任务目录不自动云端备份，也不自动删除。受支持的清理流程必须展示任务状态并取得明确确认；`ERP 写入结果未知`的任务不得清理。进入`ERP 草稿已交接`后，baox 不再追踪用户是否检查或提交 ERP 草稿。

## 当前仍需验证的边界

- PNG/JPG 图片发票、压缩包、损坏文件和多页混合文件的解析与角色处置；OFD 已明确为 v1 不支持格式。
- v1 允许的住宿和客运票种中，发票身份、参考材料关联和 ERP 枚举映射的完整样本覆盖。
- 一张合并交通发票对应多条费用事件时的行程分摊和金额守恒。
- ERP 外部重复记录的可查询接口；在接口不可用时必须继续阻塞，而不是降低门槛。外部记录只有在重新查询确认已消除后才能解除阻塞，否则转人工。
- PNG/JPG 图片发票、合并交通发票和负数行的真实样本验证，以及 ERP 外部重复记录的可查询能力。
