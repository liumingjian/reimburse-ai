# 金蝶 ERP 费用报销草稿保存契约

验证日期：2026-09-02  
补充验证日期：2026-09-04  
表单：`ER_ExpReimbursement`（金蝶云星空 H5）

## 结论

在用户明确授权下，现场已在多个样本上保存费用报销草稿；没有提交、审核、下推、付款或删除业务单据。保存成功时系统生成单据编号，页签由“新增”变为“修改”。本文不记录单据号、发票号、收票单号、姓名、工号、供应商、项目名称、Cookie、token 或临时 URL 参数。

v1 的保存前契约是：

- 表头事由是实际必填项。默认值为用户确定的 `客户支持`，不能因页面展示了文本就认为 ERP 业务模型已经接收该值。
- 明细必须有项目、费用项目、发票类型和费用承担部门；开始/结束日期可保留 ERP 新增单默认值。测试项目序号能唯一解析，且本样本没有带出销售合同。
- 本样本费用项目为 `FY010001`（住宿），费用承担部门保留 ERP 默认值。
- 发票类型先设为“增值税发票”，再写金额；修改发票类型会清空已有税额。
- `费用金额` 是不含税金额，不是价税合计。`申请报销金额 = 费用金额 + 税额`；正常申请付款场景下，`申请付款金额 = 申请报销金额`。
- 纯发票固定从“不生成费用明细 -> 电脑端选取”导入。导入后必须验证明细仍为原行数、收票新增/复用成功且金额没有被改写。
- 本次重新授权后的非重复曹操主发票自动上传并关联导入成功；首次自动生成的明细没有形成可保存的业务映射：收票为不含税 50.12、税额 1.51、价税合计 51.63，而明细为费用金额 51.63、税额 0，发票类型为“普通发票”，项目、费用项目和事由为空。补齐任务常住城市、交通项目和字段映射后，草稿最终保存成功；这仍然证明导入成功不能直接推广为字段契约。
- 只有生成单据编号且页签进入“修改”状态，才算草稿保存成功。DOM 中的可见值、点击“保存”或无报错都不是充分成功信号。

## 字段与顺序

| 字段 | 稳定 key | 本次契约 |
| --- | --- | --- |
| 表头事由 | `FCAUSA`（控件 ID 片段） | 必填；v1 默认 `客户支持`。必须通过真实控件事件写入，并在保存后复核。 |
| 项目 | `F_BJYC_PROJECTID` | 必填；按项目序号精确解析。本次住宿样本未带出销售合同；当前交通样本按用户统一设置为 `111454`。用户规则说明：项目有关联合同时由 ERP 自动带出，否则合同保持空。 |
| 费用项目 | `FEXPID` | 必填；按编码精确解析。本次住宿样本 `FY010001` 显示为“住宿”；当前交通样本因常住城市为广州，选择 `FY008001`“本地市内交通”。 |
| 发票类型 | `FINVOICETYPE` | 必填；本次数电专票映射为“增值税发票”；当前旅客运输服务电子普通发票映射为“其他运输票”。应在金额之前设置。 |
| 费用承担部门 | `FEXPENSEDEPTENTRYID` | 必填；本次保留 ERP 默认部门，不从票面推断。 |

| 税额 | `FTAXAMT` | 写入票面税额 `206.04`。 |
| 申请报销金额 | `FEXPENSEAMOUNT` | 只读计算列，系统得到 `3640.00`。 |
| 申请付款金额 | `FREQUESTAMOUNT` | 只读计算列，正常申请付款下系统得到 `3640.00`。 |

稳定操作顺序：

1. 填表头事由，并使控件真实失焦。
2. 按项目序号精确选择项目；读取销售合同是否由 ERP 自动带出，不自行猜测合同。
3. 按费用项目编码精确选择费用项目，保留并复核费用承担部门。
4. 设置发票类型。
5. 先写费用金额，再写税额；逐项读取两个系统计算金额。
6. 通过固定入口导入纯发票；核对明细行数、收票行数和金额守恒。
7. 展示最终差异并取得保存草稿的即时确认。
8. 点击保存后，用“单据编号已生成 + 页签为修改”确认结果；任一信号缺失都视为未保存或结果未知。

## 金额控件和舍入

- 两个可写金额字段都是 `kdnumberfield`，精度为 2。
- 程序化整值 `fill()` 曾出现“编辑态可见、失焦后丢失”的假成功。现场可靠路径是发送真实逐键输入并按 Enter 提交，再读取非编辑态单元格。
- 写费用金额会清空先前税额，因此必须先费用金额、后税额。
- 费用金额填价税合计 `3640.00`、税额填 `206.04` 时，系统曾算出 `3846.04`，直接证明费用金额语义是不含税金额。
- 正确守恒式为 `3433.96 + 206.04 = 3640.00`，且申请付款金额同为 `3640.00`。
- 正数第三位小数现场表现为截断而非四舍五入：`3433.955 -> 3433.95`、`206.045 -> 206.04`。生产代码仍应在进入 ERP 前完成两位小数和金额守恒校验，不依赖 ERP 替应用修正。

## 收票与重复票

- 使用“不生成费用明细”后，导入前后费用明细都保持 1 行；导入后收票为 1 行。
- 收票金额为不含税 `3433.96`、税额 `206.04`、价税合计 `3640.00`，与明细四金额守恒。
- ERP 对重复或既有外部记录并非只有一种表现：早期样本曾出现“已有对应收票单并执行覆盖”，本次清空助手队列后再导入同一账号下的 AA 主发票则显示“重复报销，禁止导入”并提供“申请解绑”。两种表现都说明结果依赖当前收票关联和外部历史状态，不能作为稳定业务契约。
- 本次曹操主发票在重新授权后的非重复关联上下文中成功导入，收票表回写 1 行；但回写后的业务明细没有继承票面不含税/税额语义，直接把价税合计写入费用金额且税额为 0。导入后必须把收票回读和明细回读都作为独立后置条件。
- 因此 baox v1 必须把当前任务内重复、外部既有发票记录、ERP 重复警告和重复来源不确定统一记录为阻塞性的 `待确认项`。列表放行和导入前必须先拦截；不得静默复用、覆盖或点击“申请解绑”。只有用户在系统外完成明确处置后，重新运行全量材料检查，才允许重建 ERP 就绪快照。
- 发票助手的企业收票池和移动票夹未提供本次上传文件的可复用记录；跨页面恢复时不能假设刚上传但未导入的文件仍在票池。

## 保存校验和成功信号

| 场景 | 实际结果 | Agent 契约 |
| --- | --- | --- |
| 表头事由为空 | 弹出“字段必录提示”，指出基本信息的事由为空；不生成单据编号 | 保持在草稿前状态，返回结构化字段错误，不重试提交类动作。 |
| 事由只在 DOM 中显示、未进入业务模型 | 保存仍报同一必录错误 | 可见文本不能作为字段已提交的证据；必须依赖保存结果或读取业务态。 |
| 所有本次必填和金额满足 | 生成单据编号，页签变为“费用报销单-修改” | 两个信号同时成立才标记 `draft_saved`。 |
| 同票已有收票单或外部重复 | 早期样本出现覆盖提示；本次样本出现“重复报销，禁止导入”，并未写入收票行 | 统一标记为阻塞性的外部重复事实；不自动覆盖、复用或解绑，必须由用户明确处置后全量复检。 |
| 本次项目与金额 | 未出现预算超限或其他预算提示 | 只说明本样本未触发预算错误；不能推广为“无预算校验”。 |

## 合并交通票的多明细表达

本次没有可授权使用的合并交通票样本，因此没有在生产 ERP 中制造合成交通明细。v1 采用以下确定性契约，并把真实样本验证留给验收语料：

- 一张合并交通发票仍只上传一次、形成或复用一条收票记录。
- 每个可辨识行程段形成一条候选明细和一条 ERP 费用明细；所有明细共同引用同一材料/发票证据。
- 每行必须有独立的出发地、目的地、日期、费用项目和分摊金额；不能把多个行程段拼成一个自由文本字段。
- 明细分摊后的不含税、税额和价税合计必须分别与收票金额守恒。分摊无法精确到分时，阻塞进入 ERP 并要求人工确认。
- 票面没有逐段金额时，用户必须直接提供每段价税合计；Agent 不自行平均、按比例、按距离、按时长或让模型编造，未提供时生成 blocking `allocation_required`。
- 仍使用“不生成费用明细”导入发票，避免助手重建或合并 Agent 已确认的多行明细。

真实合并交通票、多段分摊和恢复行为必须纳入 [v1 的验收语料和发布门槛](https://github.com/liumingjian/reimburse-ai/issues/14)，不能仅凭本次住宿样本宣称已通过。

```
{ "parameters": ["{\"FormId\":...,\"FieldKeys\":\"FNumber,FName,FDocumentStatus,FForbidStatus\",\"FilterString\":...,\"StartRow\":0,\"Limit\":n}"] }
```

两个选择器背后的业务对象取自 `ER_ExpReimbursement` 的表单元数据
（`DynamicFormService.QueryBusinessInfo` 的 `LookUpObjectFormId`），不是猜的：

| 明细字段 | 业务对象 | 说明 |
| --- | --- | --- |
| 费用项目 `FEXPID` | `BD_Expense` | `FNumber` 即费用项目编码 |
| 项目 `F_BJYC_PROJECTID` | `BJYC_ProJect` | 公司自定义对象，大小写照抄；`FNumber` 即用户填的项目序号 |

这条通道只证明主数据**存在且可引用**，不证明它在费用明细上保存得进去；

## 2026-09-05 字段写入通道（不保存的排练）

在同一张**新增**单上反复排练"按契约顺序填字段、逐项回读、不保存"，用来把写入侧的坑一次性暴露出来。这一节只记录写入通道本身的事实，不改动上面的字段契约。

### 网格的行列定位

- 明细网格的单元格**没有字段 key**，只能按列标题定位。
- **表头行和数据行不在同一个滚动容器里**：横向滚动之后表头仍在 `x 44..2614`，数据行已经滚到 `x -812..1308`。因此按坐标把单元格对回列是错的，只能**按 DOM 顺序对齐**，并要求两边列数相同，对不上就整个不认——错位的列会把税额写进申请付款金额，而且看上去一切正常。
- 合计行的判据是 `tr.k-footer-template`，不是"没有序号"：行进入编辑态时序号也读不出来。
- 明细行的编辑态是 `tr.k-grid-edit-row`，这是**整行**的状态；某一格的编辑器有没有绑好是另一回事。

### 让金蝶控件真正收到值

| 控件 | 现场可用的写法 | 踩过的坑 |
| --- | --- | --- |
| 表头事由 `FCAUSA` | 真实点击 -> 全选 -> 逐键输入 -> **Tab** 失焦 | 用 Enter 不够，契约要求真实失焦 |
| 项目 / 费用项目（F7） | 真实点击 -> 全选 -> 逐键输入**编码** -> Enter | 回读出来是**名称**不是编码，所以预期回读成什么必须另有出处 |
| 发票类型 | 点开下拉 -> 按**完全一致**的文本点中候选项 | 它是 Kendo dropdown 不是文本框，逐键输入对它完全无效，且不报错 |
| 费用金额 / 税额 | 真实点击 -> 全选 -> 逐键输入 -> Enter | 回读带货币符号（`¥18.25`） |

- **全选必须显式带 `commands: ['selectAll']`**。只发 Meta+A 的按键事件，控件根本不会全选：事由写成了"客户支持客户支持"，费用金额拼成 `0.0018.25` 后被控件整个丢弃。旧值恰好是 `0` 时拼接结果仍然能解析，这类"碰巧对了"会把问题一直藏到金额不是 0 的那一次。
- **点开之后编辑器不是立刻绑好的**。焦点落在 `td` 上时 `td.contains(activeElement)` 一样为真，这时逐键输入全部落空且不报错。可用判据是焦点落在这一格里的 `INPUT`/`TEXTAREA` 上。网格安静时点一下，编辑器 400ms 内就绑好；重算还在跑时点，点击要么被吞掉、要么绑好的编辑器随即被这轮重算收走。
- **回读期间不能滚动**。定位单元格用了 `scrollIntoView`，如果回读轮询里每轮都滚一次，等于每轮都把自己刚写的编辑取消一次。滚动只在动手之前做一次。
- **提交之后不能立刻回读**：实测 800ms 时单元格还是空的，1200ms 才回填。
- 发票类型的全部候选项（2026-09-05 实测六项）：普通发票、增值税发票、机票、火车票、其他运输票、其他。

### 顺序的一条前提

"先费用金额、后税额"说的是**干净的行**。行里已经有税额 `58.05` 时把费用金额改成 `50.12`，ERP 直接拒收：输入框里明明是 `50.12`，回车后单元格弹回 `644.95`，**不报任何错**。在同一行上反复排练必须先把税额清零，再写费用金额。

### 明细行会卡死，而表头照常

排练到后段出现过一种状态：**同一行的每个明细字段都写不进去了**——编辑器照常打开、
逐键输入照常进去、回车照常提交，然后单元格**静默回滚**成原值，页面上没有任何提示、
没有弹窗、没有报错。费用金额连写 `3433.96`、`999.99`、`3433.96` 三次都停在 `¥50.12`；
紧接着改费用项目（几分钟前刚成功过的同一个操作）同样回滚。

同一时刻**表头是好的**：`FCAUSA` 写成"客户支持A"回读一致，再写回"客户支持"也一致。
所以卡住的是明细行，不是表单实例，也不是登录态。

这条对实现的意义比对排练大：

- 它证明"点了、打了字、回车了、没报错"这一整串都不能当作写入成功。**只有回读能分辨**，
  而 baox 的判定本来就取离开编辑态之后的整行回读——这次正是靠它发现的。
- 遇到这种状态**不能重试值**。同一个值反复写只会一次次静默回滚，看上去像在工作。
  正确处置是停下来交人工：换一张干净的新增单重来。
- 触发条件还没定位（怀疑与在同一行上反复改费用项目/发票类型有关，也可能是行级校验
  进入了未决状态）。定位需要一张干净的新增单，留待下一轮。

### 排练里坐实的字段结果

- 项目按项目号 `111454` 唯一解析，显示为完整项目名并以 `-111454` 结尾；**销售合同保持为空**，与用户规则一致。
- 费用项目按编码写入，回读出的名称与只读主数据核对（V-43）给出的名称逐一相同：`FY008001` -> 本地市内交通，`FY010003` -> 长途交通。
- 金额守恒在真实控件上复现：`644.95 + 58.05`，系统算出申请报销金额和申请付款金额均为 `703.00`。

## 2026-09-05 发票进入单据的通道（B：上传与导入）

### 发票助手根本不是 ERP 的页面

「收票信息 -> 选择发票」弹出的「发票无忧助手」是一个**跨域 iframe**，地址在
`www.piaozone.com/m4-web/fpzs/index?userKey=...&linkKey=...`。这有两个后果，都不是细节：

1. **发票文件会离开公司 ERP**，交给第三方（发票无忧）去识别。这条通道本身就是公司报销
   流程的一部分，但 baox 必须如实把它说成"上传到第三方"，不能说成"上传到 ERP"。
   这也再次说明为什么助手的识别结果不能当 baox 的证据来源（用户的既有规则）。
2. 它是**独立的 CDP 目标**。`Page.getFrameTree` 里没有它，主文档只看得见一个标题。

### 跨域 iframe 的输入必须发给它自己

发到**主页面**目标的 `Input.*` 事件**到不了**这个 iframe——实测在 iframe 里挂捕获监听，
点主页面坐标时一个 `mousedown`/`click` 都收不到，页面也没有任何变化，看上去就是"点了没反应"。
必须 `Target.attachToTarget`（flatten）拿到子会话，把事件发给子会话，并且**用 iframe 自己的
视口坐标**（不是加了偏移的顶层坐标）。发对之后同一个点击立刻生效。

### 上传不用点，直接喂文件

「电脑端选取」之后 iframe 里出现一个隐藏的 `input[type=file]`
（`accept=.ofd,.xml,.zip,.pdf,.xls,.xlsx,.png,.jpg,...`，`multiple`）。走
`DOM.setFileInputFiles` 直接喂路径即可，**不会**弹 macOS 原生文件框，也就不需要
`Page.setInterceptFileChooserDialog`。实测一张真发票（曹操出行电子发票）投喂后约 6 秒识别完成，
助手列出：销方 苏州市吉利优行电子科技有限公司、价税合计 `51.63`、税额 `1.51`、开票日期 `2026-09-02`。
**同一张票再喂一次不会变成两条**（助手按发票号码去重）。

### 助手的会话是一次性的，而且失效时是静默的

助手首页自己写着"关闭窗口后，再次打开请重新扫码"。实测窗口关闭后：

- 再点「选择发票」**什么都不弹**——没有窗口、没有报错、没有提示。页面控制台里能看到
  `PWYDataEntry::,连接成功!` 和一条带 `invoiceSerialNos` 的回传，随后
  `onRefreshGridData() ...-FRECINVINFO`，但**收票网格始终是空的**（只有合计行）。
- 也就是说"点了导入、控制台看得见数据回传"同样不能当作导入成功，判据只能是收票网格的回读。

### 助手在一个页面实例里只能用一次

这条已经复现稳定：**「发票导入单据」把助手关掉之后，同一个页面里它再也起不来**。表现是
点「选择发票」后 Kendo 窗口照常弹出、标题也是"发票无忧助手"，但里面的 iframe 永远不加载
——一条 `piaozone.com` 的请求都不发。同时 ERP 控制台开始反复报

```
From KDDynamicForm Control[FEINVOICEENTITY] not found!
From KDDynamicForm Control[FREIMBANDRECINVINFO] not found!
setBarItemStates conn't find ...-FRECINVINFO_ENTRYBAR-tbReceiveInvoice control
```

~~也就是这张单的收票区控件整个丢了。~~ **这句是错的，2026-09-05 旁观时纠正**：这三行是
KDDynamicForm 的**例行日志**，每次刷新收票网格都会打，而且同一行日志里就带着网格数据
（`rowcount` 有 0 也有 2）。它既不表示控件丢了，也不表示出错——把它读成故障是我的过度解读。
助手起不来的真实原因是另一回事（见下一节：`Target.attachedToTarget` 报的 url 还是 `about:blank`）。

用工具条的「新增」换一张干净的新增单**也救不回来**
（换单没有弹"是否保存"，页签仍是"费用报销单-新增"，但助手照样起不来），所以坏的是页面实例，
不是单据实例。唯一已知的恢复手段是刷新页面——而刷新在这个 ERP 上等于掉登录，要用户重新登录。

对实现的意义：**发票导入在一次页面加载里只有一次机会**。baox 必须把"助手起不来"当成
一个明确的失败态停下来转人工，而不是重试——重试永远不会成功，只会把时间耗在等待上。

### 「发票导入单据」这一步：确认勾上了，导入仍然是空的

第三轮在一张干净的新增单上做了决定性的一次：助手识别出票面 `51.63`，发票行的
`input.ant-checkbox-input` 由 `checked=false` 点成 **`checked=true`**（勾选这件事本身有了硬证据），
然后点「发票导入单据」。结果：

- 助手窗口关闭（说明按钮确实点到了）；
- 24 秒内持续回读，**收票网格始终只有合计行**；
- 明细网格里只有 ERP 自己的默认空行（日期今天、发票类型默认"普通发票"、金额为空）；
- 页面上没有任何弹窗、没有报错。

所以"根本没选中票"这个解释被排除了：**票选中了，导入照样什么都没进来**。

~~一条还没验证的线索：早前的控制台里，ERP 侧的回调是
`PWYDataEntry::,copys:undefined,...`——`copys` 是 `undefined`，怀疑导入要映射到
"当前那一行费用明细"上。~~ **这两条猜测都在 2026-09-06 被证伪，见下一节。**

要把这一步钉死，最省事的办法是**看用户手工做一次**：同样的表单、同样的票，人点一遍，
我在旁边只读记录 DOM 和控制台。这比继续盲点划算——助手一个页面实例只能用一次，
每试一次都要用户重新登录一遍。

### 原先的记录（第二轮）

唯一一次点成的导入，事后收票网格**只有合计行**，明细网格里那条行是 ERP 自己的默认空行
（日期是今天、发票类型默认"普通发票"、金额为空）。但那一次**没有确认发票行有没有被勾上**
（助手底部的"所有已选发票"计数在勾选前后读数没变化），所以"导入没产生任何东西"和
"根本没选中票"这两种解释还分不开。发票行的勾选控件已经定位到了：助手用的是 Ant Design 表格，
行首 `td.ant-table-selection-column` 里有 `input.ant-checkbox-input`，判据应当取它的 `checked`，
不要看底部计数。

所以「是否生成费用明细」这个选择长什么样、「不生成费用明细」怎么选，**仍然未验证**。

### 单据工具条在正文滚下去之后坐标是负的

表单正文是**内层容器**在滚，`window.scrollY` 恒为 0，所以工具条（新增/保存/退出）的
`getBoundingClientRect().y` 会变成负数，照着点等于没点，而且不报错。要点工具条必须先把
带 `scrollTop` 的那个容器归零。这与"表头行和数据行不在同一个滚动容器里"是同一类坑。

### 模态窗开着的时候，单据工具条收不到点击

助手窗口开着时点「删除行」完全无效且无提示。凡是要操作单据本体，必须先确认没有 `.k-window` 开着。

### 关于上一轮那个"静默回滚"

补一条反证：卡住那一行被删掉之前又读了一次，费用项目显示的是 **`长途交通`**——正是当时被判为
"回滚了"的那个值。所以那个状态里至少有一部分是**延迟落值**，不是纯粹的丢弃。这不改变处置
（照样停下转人工），但它把结论收紧了：写入当场的回读为假，**不足以**证明值没有写进去。

### 刷新页面 = 掉登录

`Page.reload` 之后 ERP 直接回到登录页（[V-42](verification-ledger.md)：登录页和主控制台同一个 URL）。
单据里没保存的东西全部丢失。所以"刷新一下重来"在这个 ERP 上不是零成本操作，要由用户重新登录。

## 2026-09-06 人工做成的一次导入（旁观实录）

用户在一张干净的新增单上手工报销了一张票，全程 8 分钟只读旁观（每 1.5 秒求值一次两个网格、
可见 `.k-window`、焦点元素、以及 piaozone 子目标在不在；不点任何东西）。
这是**第一次拿到成功样本**，它推翻了上一节的两个猜测。

### 顺序是「先导发票，后填明细」

| 时刻 | 现场 |
| --- | --- |
| 2s | 明细行只有 ERP 默认值：序号、开始/结束日期=今天、发票类型=普通发票、费用承担部门。**项目、出发地、目的地、费用金额全空** |
| 265s | 工具条动作，控制台 `lockControl,FRECINVINFO_ENTRYBAR` |
| 266s | `.k-window` 标题「发票无忧助手」出现，piaozone 子目标出现 |
| 269s | `PWYDataEntry::,连接成功!`，随即回调带回票面数据 |
| 269–298s | **29 秒 ERP 页面零变化**——上传、勾选、点导入、以及后续的所有选择都发生在 iframe 内部 |
| 298s | 助手窗口消失，**同一次快照里收票网格长出数据行** |
| 310–411s | 用户这才开始填明细行 |

### `copys: undefined` 是正常形态，不是故障

成功的这一次，回调和失败那次**完全一样**：

```
PWYDataEntry::,copys:undefined,msg:{"data":{"invoiceSerialNos":"7b85…","data":[{
  "salerName":"武汉风韵出行信息科技有限公司","kprq":"2026-09-04",
  "hjbhsje":18.25,"kphjse":0.55,"fp_zl":"26",…}]}}
```

把 `copys` 读成"少了个入参"是过度解读，同上一节那三行 `Control[...] not found`。
**这条线索作废。**

### 导入不需要"当前费用明细行"

导入发生时明细行还是空白的（只有 ERP 默认值），收票行照样进来了。
"导入要映射到当前那一行费用明细上"这个假设**证伪**。

### 失败点只可能在 iframe 内部

269s 到 298s 之间 ERP 页面一动不动，说明点完「发票导入单据」之后的全部交互
——包括**「是否生成费用明细」这个选择**——都在发票助手自己的页面里，
不是 ERP 的 `.k-window`。之前的自动化点完导入就只轮询 ERP 的收票网格，
**从来没回读过 iframe 自身的内容**，所以"点了没反应"更可能是
iframe 里弹了下一步而没人应答，或者那一下坐标压根没落在按钮上。

对实现的意义：**点完导入之后，第一件事是回读 iframe 的可见文本**，不是去猜 ERP。

### 导入进来的收票行长什么样

```
收票单=SPD202609040022  发票号码=2642…8021  销售方名称=武汉风韵出行信息科技有限公司
开票日期=2026/9/4  不含税金额=18.25  税额=0.55  价税合计=18.8
发票状态=正常  是否勾选=否  是否勾选认证=否  查验状态=已查验
发票是否有修改=未修改  发票类别=全电普通发票
```

`收票单` 是导入时由 ERP 生成的单号，不是发票自带的。

### 金额对账的锚点：费用金额是人对着填的，不是带过来的

明细行填写顺序：项目 → 开始日期/结束日期（都改成 2026/8/22，与今天无关）→
出发地 `番禺广场` → 目的地 `傍西酒堂` → **费用金额手打 `18.8`** → 费用项目 `本地市内交通`。

`费用金额` 填完的下一秒，`申请报销金额` 和 `申请付款金额` 自动跟成 `¥18.80`——
这两个是派生的，不要写。而 `费用金额` **必须等于收票行的 `价税合计`**，
ERP 不会自动带，是人对着填的。这就是 baox 该做的对账：拿收票网格的 `价税合计`
去校验明细行的 `费用金额`，两者不等就停下。

### 两个网格是同时可见的

`.kd-grid-panel` 里 `#0` 是明细、`#1` 是收票，同时在 DOM 里且都可见，
读取不需要在区域之间来回点。

### 读数噪音：`已生成发票` 分不出勾没勾

快照里的 `已生成发票=<on>` 来自 checkbox 的 `value` 属性，`on` 是浏览器默认值，
勾与不勾都是它。**不能拿它当勾选证据**，要判必须读 `checked`——
和助手里那个 `input.ant-checkbox-input` 是同一条规矩。

## 恢复与残余风险

- 新增单页面若未保留到下一轮，所有未保存字段和助手选择会丢失；上传文件也未必出现在可查询票池。跨轮人工接管前必须显式保留浏览器标签，并在恢复后从 ERP 状态重新核对。
- 当前重新登录后的 ERP 草稿已保留 1 条曹操收票和 1 条明细；按常住城市广州、交通项目 `111454` 完成映射后已保存，并以单据编号生成和页签进入“修改”作为后置条件。
- 表头事由控件曾出现 DOM 已显示值、ERP 模型仍为空的分离状态。实现需在控件层使用真实输入事件或可访问控件值写入并触发失焦，把保存后的业务状态作为最终判据。
- 本次只验证了一个项目、一个费用项目、一张住宿发票和正常申请付款；有关联合同自动带出、超预算、合并交通票和其他发票类型仍需各自验收样本。
- 现场最终仅保存 1 张草稿。没有提交、审核、下推、付款或删除。
