# MarkItDown PDF 迁移验收

日期：2026-09-09。范围：基于当前 main 的开发工作区；本地 PDF 流程，不包含 ERP 保存或发布验收。

## 实现范围

- 正常 PDF 分支使用随包 Python/uv 锁定运行时转换，生成 Markdown、编号副本及可回看的原始页 PNG。
- Agent 按封闭模板提取候选；内核验证原件、Markdown、依赖锁及页图哈希，核对字段格式、引用、金额和段数。
- `read_markdown` 明确要求先读取、填写，再提交候选。分类明细确认在项目选择之前。
- 原件或派生物失效、候选校验失败时，保留明确待办；图片继续走视觉读数流程。
- Skill 的 PDF 分支按需加载，跨行/串列触发原件页面核对，完成条件写在各步骤末尾。

## QA 中发现并修正

第二轮真实 Markdown 提取把 191.69 元行程单的第 2 段起终点颠倒了，金额与 quote 存在性均不足以发现。Orchestrator 打开原始渲染页确认：第 1、2 段均为中国农业银行数据中心到麦新格精品酒店。修正版重新核对原件、修正方向并保留归并依据。

该失败促成生产页图 fallback 和 Skill 的强触发：跨行、串列或方向归属不清时先回看原件。此次不将结果表述为“仅凭 Markdown 的全自动准确率 100%”。

模板使用还暴露了信息性说明与未解决问题混写：原件缺失的非必填字段用 `fieldStatus` 表达，已核对的归并说明放 `fieldBasis`，`issues` 专用于仍需处置的问题。原失败版及修正版均保留。

独立复核还构造了净额/税额互换和票种改选的反例：金额 token 存在及加法守恒不证明其标签归属，闭集票种也不证明类型解释正确。因此主发票候选提交前必须回看原件标题和金额标签，分类确认表须展示票种、净额、税额和合计。这里依靠原件核对及明确确认，不能宣称 JSON 校验已经证明全部业务语义。

## 独立失效检查

- 金额仍守恒但候选值不在 quote 中：拒绝。
- 日期格式合法但没有对应引用：拒绝。
- 未声明字段、无对应页清单的页码：拒绝。
- 修改编号 Markdown：退回转换；修改候选记录：候选无效；修改页 PNG：退回转换。
- 保持业务值不变，仅换一条合法引用：确认摘要变化。
- 交通增值税发票不会因票种被要求填写酒店离店日期。
