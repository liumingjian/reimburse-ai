# 本地报销应用：去掉 Agent 的完整报销流程

状态：设计共识已确认，部分已实施。日期：2026-09-11，2026-09-19 按 ADR-0019～0024 反校。

本文是产品权威，但下列取舍已被后续 ADR 推翻，正文已就地更正：ERP 浏览器不再由 baox 启动，而是员工自己的浏览器加一个扩展（ADR-0019、ADR-0021）；ERP 自动化控制权按应用账号而非全局（ADR-0019）；服务不再只跑在员工本机（ADR-0018、ADR-0022）。

## 目标

把 baox 从「Agent 驱动的 Skill」改成「本机运行的报销应用」。员工在浏览器页面里上传材料、核对整单明细，然后选择 **去打印** 或 **去报销**；全程不经过 Agent，也不调用大模型。

动机：报销是固定场景。现有流程能完成工作，但每一步都要经过一轮模型——`run` 步骤只是原样转发 `step.argv`，`ask_user` / `confirm_table` 只是原样转贴——耗时长，且大量规矩（原样念、不代答、不改写问题）只是在防模型转述出错。这些交给页面和确定性代码，天然成立。

## 范围

- ~~v1 只支持 macOS，只在员工本机运行。~~ 已改：服务跑在一台共享的 Linux 服务器上、服务多名员工（ADR-0018、ADR-0022），ERP 部分由员工自己浏览器里的扩展执行，限 Chrome 与 Edge（ADR-0021）。
- 只支持下表四类费用；其余材料一律形成待确认项，由员工排除或自行手工处理，不猜排版和费用类别。
- 暂缓：明细汇总表（将单独做成 Word 表单，另行设计）、打包成可双击的 macOS 应用、Windows 支持、大模型兜底。

| 费用 | 主要报销凭证 | 参考材料 | 打印：上半页 / 下半页 |
| --- | --- | --- | --- |
| 住宿 | 住宿发票（全电专票/普票） | 结账单 | 发票 / 结账单 + 支付截图（可选） |
| 网约车 | 旅客运输电子发票 | 行程单（至多一份，可含多段行程） | 发票 / 行程单 |
| 高铁 | 铁路电子客票 | 无 | 客票 / 空 |
| 出租车 | 纸质机打车费发票照片 | 无 | 车票 / 空 |

## 实测依据

2026-09-11 在本机样本（9 份电子材料 + 2 张出租车照片，含个人信息，不入库）上验证：

- **7 份 PDF 全部有干净文本层**，不需要 OCR；金额、日期、号码都带明确标签。
- **全电发票二维码 4/4 可解码**，格式 `01,类型,,发票号码,价税合计,开票日期,,校验码`。类型 `31` 为专票、`32` 为普票。二维码金额是**价税合计**，不是不含税金额；不含税金额和税额仍从票面取。铁路客票未解出二维码，其文本层已足够。
- **RapidOCR（PP-OCRv6 small）读截图**：关键字段全部正确，置信度基本 ≥ 0.97。红章压住的标题会断字，票种改以「旅客运输服务」字样和二维码类型判定。
- **出租车照片**：发票代码、号码、金额、里程全部正确。其中一张日期读成 `225-11-06`：票面年份前两位与后半段错位打印，属于票面问题，规则需按年份后两位补全，而不是去修 OCR。
- **材料间可确定性配对**：打车发票与行程单按价税合计一一对应，且行程人手机号相同；AA 三段 26.69 + 20.85 + 21.65 = 69.19，按分守恒；住宿发票 3640.00 = 结账单消费合计，数量 13 天 = 08-09 入住至 08-22 离店。

## 架构

内核仍是唯一的业务事实来源：状态机、材料身份与哈希、费用事件、分摊、确定性校验、ERP 写入、ERP 对账与恢复都不变。变的是「谁来消费 `step`」。

```
浏览器页面 ──HTTP──▶ 本地应用服务（50931a3:kernel/src/serve.mjs 扩展）
                         │  循环调用 next，按 step.kind 分派：
                         ├─ run            → 服务端直接执行，自动推进
                         ├─ 字段提取        → 规则提取器（替代 read_images / extract_images / read_markdown）
                         ├─ 用户交互        → 页面（替代 ask_user / confirm_table / tell_user / dispute）
                         └─ 打印           → 打印稿生成器（新增）
```

- **启动**：终端执行一条命令（如 `baox`），在默认浏览器打开 `localhost` 页面。
- **Skill 下线**：现有 `baox` / `baox-setup` / `baox-recover` / `extract-reimbursement-images` 不再是入口。`stepToken` 的幂等和不可跳步语义保留，改由页面回传。
- **字段提取器**：规则解析器按「材料种类 + 可插拔版式」组织，全部在服务端 Node 进程内运行（OCR 用 `onnxruntime-node`，见 #147），不再需要 Python Worker。候选来源记为 `rule:<种类>/<版式>`（如 `rule:ride_itinerary/amap`）或 `user`，替代 `agent_from_markdown` 和视觉读数来源。见 ADR-0017。
- **打印稿生成器**：放在独立的 workspace package（如 `packages/print-sheet`），依赖 `pdf-lib`，以保持 Node 内核零 npm 依赖。

## 材料上传

- 员工在页面拖入或选择文件；应用把原件复制进报销任务目录，作为不可变的报销材料。
- 材料盘点的边界从「材料目录」改为「本次上传批次」。追加或删除材料形成新的盘点版本，旧候选和确认按现有规则失效。
- 支付截图不在初始上传中，见「支付截图」。

## 字段提取

每个材料种类统一定义字段、校验和手工补填表单，其下每种版式一个解析器，只认自己的版式；不认识的版式形成待确认项，由员工排除、改为参考材料，或在页面上对照原件手工补填。手工补填的值来源记为 `user`，与规则候选同样经过确定性校验。字段按来源分级可改：PDF 文字层与二维码给出的票面事实锁定，OCR 或手工补填的票面事实可对照原件纠正，描述性字段可自由改写为呈现值（ADR-0017）。下表为 v1 的版式。

| 解析器 | 输入 | 要点 |
| --- | --- | --- |
| 全电发票 | PDF 文本层；图片走 OCR | 按「合计」「价税合计（小写）」标签取三项金额，不取第一行（曹操发票含负数折扣行）。二维码交叉核对发票号码、开票日期、价税合计和专票/普票类型；不一致形成待确认项 |
| 铁路电子客票 | PDF 文本层 | 先做全角→半角规范化；取乘车日期、车次、起终站、票价 |
| 高德行程单 | PDF 文本层；图片走 OCR | 按列坐标归属单元格、按行坐标合并跨行文字（AA 行程单的起终点被拆成两行）。逐段金额之和须与发票价税合计守恒 |
| 结账单 | PDF 文本层 | 取入住日期、离店日期、消费合计。首版只覆盖全季版式，其他连锁的结账单走手工补填 |
| 出租车车费发票 | 照片 → 裁边与透视矫正 → OCR | 取发票代码、号码、日期、上下车时间、里程、金额。日期年份按后两位补全为 `20YY`，月日须合法 |

- **PDF 文本来源**：`unpdf`，带逐项坐标，已在样本上验证（#147）；须配版本匹配的 `pdfjs-dist`，并以文件路径传入 CMap 与标准字体目录。MarkItDown 不再是必经环节。
- **OCR 引擎**：`onnxruntime-node` 加载与 RapidOCR 相同、按 SHA-256 锁定的 PP-OCRv6 small ONNX 模型，进程内运行，与 Python RapidOCR 结果一致（#147）；不引入 Tesseract.js。
- **出租车城市**：由发票代码的地区码推出（样本 `131…` 对应上海），在确认页展示；推断规则须用更多样本验证。
- **出租车起终点**：内核要求客运费明细具备结构化起终点（`50931a3:kernel/src/erp-draft-flow.mjs:54-55`、`:315-316`），车票上没有，由员工在确认页必填。
- **出租车金额与票种**：ERP 发票类型为「普通发票」；不含税金额 = 价税合计 = 票面金额，税额 `0.00`，与铁路票的规则一致。

## 流程顺序、整单明细确认与两个按钮

页面流程按 ADR-0014 的顺序，与 Skill 的旧顺序（内核 `50931a3:kernel/src/state.mjs`）只差一处：报销信息核对移入「去报销」的 ERP 后台任务。

```
上传 / 材料盘点 → 待确认项 → 项目归属 + 报销事由 → 报销材料准备
→ 唯一一次整单明细确认 → 去打印 ｜ 去报销（ERP 后台任务：启动浏览器并登录 → 报销信息核对 → 导入、填写、保存 → 严格回读 → 完成 / 对账）
```

- 项目归属在整单明细确认**之前**，两条路径都要经过：打印稿本身不需要项目，但确认必须覆盖项目。材料准备由服务端在提交项目归属后自动执行。
- 报销信息核对是 ERP 后台任务的第一步，在导入任何发票之前执行（ADR-0014、ADR-0016），因此整单明细确认和去打印都不需要 ERP 会话。核对不一致时，任务在任何 ERP 动作尝试之前中止，不进入对账，回到项目归属并展示不一致表；改派项目改变摘要，旧确认随之失效。
- 只有一次整单明细确认（内核 `preparation_confirmation`）。确认的摘要绑定项目归属与报销事由（内核 `preparationDigest` 的来源快照包含 selection）。确认后改派项目或修改事由，旧确认失效，须重新确认；提交的归属与事由都没变时，确认仍然有效。
- 确认后出现 **去打印** 和 **去报销** 两个按钮。两者基于同一份已确认的数据，互不依赖、先后随意、可重复点击。打印稿不需要 ERP 单号或其他 ERP 产生的信息。
- 打印稿与 ERP 填报的**内容必须一致**。确认后若材料或明细变更，旧确认失效，已生成的打印稿作废，须重新确认后再生成。
- 补充或更换支付截图、在预览中旋转或调整裁剪，都只影响打印稿，不使整单明细确认失效。

## 统一业务序号

整单确认表的 No.、打印稿页序与 ERP 明细行（含严格回读表）共用同一个业务序号，**跟随内核确认表的分类排序**（`50931a3:kernel/src/next.mjs:520-521,536-537`），内核不需要为此改动：

1. 按费用分类排序：本地市内交通 → 外地市内交通 → 长途交通 → 住宿；
2. 同一分类内保持内核的事件顺序，即先按主要报销凭证（materialId，`50931a3:kernel/src/events.mjs:356-359`），再按行程段。

同一张发票的多段因此仍然连续（一张发票只属于一个分类），打印稿一票多段写序号范围，如 `No.1-3`。序号由服务端随快照给出，页面从不自己排序或编号。发票导入 ERP 的顺序不要求一致（现为按格式分组上传，`50931a3:kernel/src/invoice-upload.mjs:2-17`）。

## 打印稿

输出一份合并 PDF，员工下载后批量打印。

**页面**

- 每张主要报销凭证一页 A4 纵向；发票和证明材料**必须在同一页，各占半页**，中间以细虚线分隔。
- 页边一行小字页眉：`No.序号 · 日期 · 费用类别 · 价税合计`；一票多段写序号范围，如 `No.1-3`。页序跟随统一业务序号。页眉不占两个半页的版面。
- 高铁票、出租车票下半页留白，不与其他发票拼页。

**放置规则**

- 每份材料放入分配给它的区域时，自动比较「竖放」和「旋转 90°」哪种缩放更大，取更大者。结账单、出租车长条票通常会被旋转。
- PDF 原件先裁掉四周空白再放置，以矢量嵌入；图片以位图嵌入。
- 照片（出租车票）先自动检测纸张边缘、做透视矫正并裁掉背景。
- 住宿页下半页左右分栏：结账单占左侧约 2/3，支付截图竖放占右侧约 1/3；没有支付截图时结账单占满下半页。

**预览**

- 下载前逐页预览。每份材料可手动旋转；照片可拖动四角微调裁剪。
- 调整结果只保存为打印设置，不改原件，也不改确认数据。

## 支付截图

- 手机支付截图，仅用于打印稿。它不参与字段提取、材料证据关联、查重，也不上传 ERP。
- 住宿三件套在材料盘点时核对（#213）：住宿发票、与它配对的结账单、它的支付截图，缺哪件就出一个待确认项，点名缺的是哪件、是哪份材料的。补上缺件（结账单追加上传后重新盘点；支付截图在这个待确认项里直接上传）这一项就消失；确实没有就选「确认没有」，记下缺件，清单照常往下走。三件齐全不出待确认项。
- 员工也可以在打印稿预览页上点「补充支付截图」上传或更换（确认页没有这个入口）；每张发票至多一张。整单明细确认之后，住宿发票的支付截图若在盘点时没有确认过「没有」，只能更换、不能移除。
- 打印稿里住宿页没有支付截图时的提醒，读的是盘点时记下的「确认没有」，不再按费用类别另判一次；允许打印。

## ERP 填报

「去报销」启动一个 ERP 后台任务（ADR-0016），页面经 SSE 跟随进度：主数据只读核对、登录探测、报销信息核对、导入发票、写明细、保存草稿、严格回读，结果不确定即停并对账。执行这些动作的是员工自己浏览器里的扩展，走内容脚本与 `chrome.debugger` 的混合通道（ADR-0021）；CDP 执行器降级为开发与测试用（#227）。整单确认之后不再追加「开始填报」之类的确认（内核 `erp_write_pending` 自动执行，交互契约不追加保存确认）。与 Skill 相比的变化：

- 页面接管原来的 `tell_user`：员工在**自己浏览器**的 ERP 会话里登录，页面提示他去登录；「我已登录，继续」只请服务端经扩展再探测一次，检测到登录即继续。这次登录本身就是 ERP 自动化授权；登录的 ERP 账号只记录、不与应用账号比对（ADR-0016、ADR-0019）。扩展通过一次性配对码换取长期令牌，服务端按应用账号路由 ERP 指令（ADR-0019）。
- 报销信息核对从整单明细确认之前移到本任务的第一个 ERP 步骤（ADR-0014）。
- 出租车照片与其他发票一样走发票识别导入，上传**原图**；矫正图只用于打印。

## 与既有 ADR 的关系

- **修订 ADR-0001、ADR-0009**：Skill 外壳和「模型只执行 `next`」让位于本地应用。内核判定下一步的原则不变，只是消费方从模型换成页面和服务端。
- **取代 ADR-0011（MarkItDown）中的 Agent 候选**：文本 PDF 的字段候选改由规则解析器产生，MarkItDown 不再是必经环节。
- **修订 ADR-0013（受管 OCR，原编号 0011）与 ADR-0004**：图片路径从「默认模型视觉」改为「OCR + 规则，失败转手工补填」，不再有模型视觉回退。
- **ADR-0010 的命令守卫**只防模型，由 ADR-0014 退役。
- **保持**：Node 内核零 npm 依赖（打印稿生成器放在独立 package）、空文本 PDF 必须阻塞、ERP 写入不重放、对账后只有原地等待和转人工两种处置。

本地应用的取舍记录在以下 ADR：

- **ADR-0014（任务模型）**：阶段与步骤由已存事实推导，不存 `stage`；报销信息核对移入 ERP 后台任务；取消任务存档。
- **ADR-0015（SQLite 事实与旧数据导入）**：只追加的 SQLite 事实、按内容寻址的文件、规则固定到任务、任务清除，以及只导入动过 ERP 的旧版任务的发票占用。
- **ADR-0016（可分离的 ERP 执行器与 ERP 后台任务）**：粗粒度执行器协议、首次改动前落库的 ERP 动作尝试、ERP 自动化控制权租约；ERP 授权只看登录，不比对身份。控制权的粒度已由 ADR-0019 改为按应用账号。
- **ADR-0017（规则解析器）**：材料种类与可插拔版式、解析结果取代 `needs_model_vision`、手工补填与字段修改分级，并修订 #20 §5；OCR 改为进程内 `onnxruntime-node`，Python Worker 下线。
- **ADR-0018（应用账号与管理员）**：本地应用账号、管理员角色与公共项目簿；每个应用账号至多一个未终态任务，发票占用全局生效；旧数据导入不再导入身份绑定。
- **ADR-0019（按账号的 ERP 控制权与扩展配对）**：ERP 浏览器改为员工自己的浏览器加扩展；控制权按应用账号，连接断开即失效；一次性配对码换长期令牌。
- **ADR-0020（重连恢复的是通道不是页面）**：有限重连窗口；重连后必须重新观测才能动作；`chrome.debugger` 断开等同于失联。
- **ADR-0021（混合填写技术与非打包分发）**：上传走内容脚本的 `DataTransfer`，明细网格走 `chrome.debugger`；限 Chrome 与 Edge；开发者模式加载，服务端强制最低版本。
- **ADR-0022（发票原件集中存放 + 全盘加密）**：原件集中存放、按所有者授权读取，不做应用层信封加密。
- **ADR-0023（严格回读容忍空的收票关联）**：明细「收票单号」在不生成模式下恒为空；空税额经守恒佐证当 0；铁路票只核价税合计；空白行不参与逐行对应；多条候选时才用填写记录消歧。
- **ADR-0024（对账中断点的用户端处置）**：六格各有文案，按处置给按钮；「重新去报销」不是第三种处置。

`CONTEXT.md` 仍需补充「打印稿」「支付截图」两个术语。
