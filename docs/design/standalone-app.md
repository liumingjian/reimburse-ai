# 本地报销应用：去掉 Agent 的完整报销流程

状态：设计共识已确认，待实施。日期：2026-09-11。

## 目标

把 baox 从「Agent 驱动的 Skill」改成「本机运行的报销应用」。员工在浏览器页面里上传材料、核对整单明细，然后选择 **去打印** 或 **去报销**；全程不经过 Agent，也不调用大模型。

动机：报销是固定场景。现有流程能完成工作，但每一步都要经过一轮模型——`run` 步骤只是原样转发 `step.argv`，`ask_user` / `confirm_table` 只是原样转贴——耗时长，且大量规矩（原样念、不代答、不改写问题）只是在防模型转述出错。这些交给页面和确定性代码，天然成立。

## 范围

- v1 只支持 macOS，只在员工本机运行。
- 只支持下表四类费用；其余材料一律形成待确认项，由员工排除或自行手工处理，不猜排版和费用类别。
- 暂缓：明细汇总表（将单独做成 Word 表单，另行设计）、打包成可双击的 macOS 应用、Windows 支持、大模型兜底。

| 费用 | 主要报销凭证 | 参考材料 | 打印：上半页 / 下半页 |
| --- | --- | --- | --- |
| 住宿 | 住宿发票（全电专票/普票） | 结账单 | 发票 / 结账单 + 支付截图（可选） |
| 网约车 | 旅客运输电子发票 | 行程单（至多一份，可含多段行程） | 发票 / 行程单 |
| 高铁 | 铁路电子客票 | 无 | 客票 / 空 |
| 出租车 | 纸质机打车费发票照片 | 无 | 车票 / 空 |

## 实测依据

2026-09-11 在本机样本（9 份电子材料 + 2 张出租车照片，含个人信息，不入库）上验证：

- **7 份 PDF 全部有干净文本层**，不需要 OCR；金额、日期、号码都带明确标签。
- **全电发票二维码 4/4 可解码**，格式 `01,类型,,发票号码,价税合计,开票日期,,校验码`。类型 `31` 为专票、`32` 为普票。二维码金额是**价税合计**，不是不含税金额；不含税金额和税额仍从票面取。铁路客票未解出二维码，其文本层已足够。
- **RapidOCR（PP-OCRv6 small）读截图**：关键字段全部正确，置信度基本 ≥ 0.97。红章压住的标题会断字，票种改以「旅客运输服务」字样和二维码类型判定。
- **出租车照片**：发票代码、号码、金额、里程全部正确。其中一张日期读成 `225-11-06`：票面年份前两位与后半段错位打印，属于票面问题，规则需按年份后两位补全，而不是去修 OCR。
- **材料间可确定性配对**：打车发票与行程单按价税合计一一对应，且行程人手机号相同；AA 三段 26.69 + 20.85 + 21.65 = 69.19，按分守恒；住宿发票 3640.00 = 结账单消费合计，数量 13 天 = 08-09 入住至 08-22 离店。

## 架构

内核仍是唯一的业务事实来源：状态机、材料身份与哈希、费用事件、分摊、确定性校验、ERP 写入、ERP 对账与恢复都不变。变的是「谁来消费 `step`」。

```
浏览器页面 ──HTTP──▶ 本地应用服务（kernel/src/serve.mjs 扩展）
                         │  循环调用 next，按 step.kind 分派：
                         ├─ run            → 服务端直接执行，自动推进
                         ├─ 字段提取        → 规则提取器（替代 read_images / extract_images / read_markdown）
                         ├─ 用户交互        → 页面（替代 ask_user / confirm_table / tell_user / dispute）
                         └─ 打印           → 打印稿生成器（新增）
```

- **启动**：终端执行一条命令（如 `baox`），在默认浏览器打开 `localhost` 页面。
- **Skill 下线**：现有 `baox` / `baox-setup` / `baox-recover` / `extract-reimbursement-images` 不再是入口。`stepToken` 的幂等和不可跳步语义保留，改由页面回传。
- **字段提取器**：沿用 ADR-0011 的分工——Python Worker 只做图片预处理和 OCR，TypeScript 规则产生字段候选。候选来源记为规则名（如 `rule:amap_itinerary`），替代 `agent_from_markdown` 和视觉读数来源。
- **打印稿生成器**：放在独立的 workspace package（如 `packages/print-sheet`），依赖 `pdf-lib`，以保持 Node 内核零 npm 依赖。

## 材料上传

- 员工在页面拖入或选择文件；应用把原件复制进报销任务目录，作为不可变的报销材料。
- 材料盘点的边界从「材料目录」改为「本次上传批次」。追加或删除材料形成新的盘点版本，旧候选和确认按现有规则失效。
- 支付截图不在初始上传中，见「支付截图」。

## 字段提取

每类材料一个解析器，只认自己的版式；不认识的版式形成待确认项，由员工在页面上对照原件手工补填。手工补填的值来源记为 `user`，与规则候选同样经过内核确定性校验。

| 解析器 | 输入 | 要点 |
| --- | --- | --- |
| 全电发票 | PDF 文本层；图片走 OCR | 按「合计」「价税合计（小写）」标签取三项金额，不取第一行（曹操发票含负数折扣行）。二维码交叉核对发票号码、开票日期、价税合计和专票/普票类型；不一致形成待确认项 |
| 铁路电子客票 | PDF 文本层 | 先做全角→半角规范化；取乘车日期、车次、起终站、票价 |
| 高德行程单 | PDF 文本层；图片走 OCR | 按列坐标归属单元格、按行坐标合并跨行文字（AA 行程单的起终点被拆成两行）。逐段金额之和须与发票价税合计守恒 |
| 结账单 | PDF 文本层 | 取入住日期、离店日期、消费合计。首版只覆盖全季版式，其他连锁的结账单走手工补填 |
| 出租车车费发票 | 照片 → 裁边与透视矫正 → OCR | 取发票代码、号码、日期、上下车时间、里程、金额。日期年份按后两位补全为 `20YY`，月日须合法 |

- **PDF 文本来源**：优先复用内核零依赖的 `kernel/src/pdftext.mjs`，它保留逐项坐标（`:410`、`:490-502`），足以按列解析；须先在样本上验证。验证不通过时，才在受管 Python 运行时中改用带坐标的解析器。MarkItDown 不再是必经环节。
- **OCR 引擎**：继续使用受管 RapidOCR，不引入 Tesseract.js。
- **出租车城市**：由发票代码的地区码推出（样本 `131…` 对应上海），在确认页展示；推断规则须用更多样本验证。
- **出租车起终点**：内核要求客运费明细具备结构化起终点（`kernel/src/erp-draft-flow.mjs:54-55`、`:315-316`），车票上没有，由员工在确认页必填。
- **出租车金额与票种**：ERP 发票类型为「普通发票」；不含税金额 = 价税合计 = 票面金额，税额 `0.00`，与铁路票的规则一致。

## 整单明细确认与两个按钮

- 只有一次整单明细确认，展示内容沿用现有定义。确认后出现 **去打印** 和 **去报销** 两个按钮。
- 两个按钮基于同一份已确认的数据，互不依赖、先后随意、可重复点击。打印稿不需要 ERP 单号或其他 ERP 产生的信息。
- 打印稿与 ERP 填报的**内容必须一致**。确认后若材料或明细变更，旧确认失效，已生成的打印稿作废，须重新确认后再生成。
- 补充或更换支付截图、在预览中旋转或调整裁剪，都只影响打印稿，不使整单明细确认失效。

## 统一业务序号

打印稿页序与 ERP 明细行共用同一个业务序号，由内核统一生成；现有按内部材料编号排序（`kernel/src/events.mjs:357-359`）改为：

1. 以主要报销凭证为单位分组，同一张发票的所有候选明细保持连续；
2. 组间按该发票最早的费用日期升序，同日按费用类别，再按材料标识兜底，保证确定性；
3. 组内按行程先后。

发票导入 ERP 的顺序不要求一致（现为按格式分组上传，`kernel/src/invoice-upload.mjs:2-17`）。现有明细与材料包两处排序比较方式不一致（`<` 与 `localeCompare`），随本次统一。

## 打印稿

输出一份合并 PDF，员工下载后批量打印。

**页面**

- 每张主要报销凭证一页 A4 纵向；发票和证明材料**必须在同一页，各占半页**，中间以细虚线分隔。
- 页边一行小字页眉：`No.序号 · 日期 · 费用类别 · 价税合计`；一票多段写序号范围，如 `No.2–4`。页眉不占两个半页的版面。
- 高铁票、出租车票下半页留白，不与其他发票拼页。

**放置规则**

- 每份材料放入分配给它的区域时，自动比较「竖放」和「旋转 90°」哪种缩放更大，取更大者。结账单、出租车长条票通常会被旋转。
- PDF 原件先裁掉四周空白再放置，以矢量嵌入；图片以位图嵌入。
- 照片（出租车票）先自动检测纸张边缘、做透视矫正并裁掉背景。
- 住宿页下半页左右分栏：结账单占左侧约 2/3，支付截图竖放占右侧约 1/3；没有支付截图时结账单占满下半页。

**预览**

- 下载前逐页预览。每份材料可手动旋转；照片可拖动四角微调裁剪。
- 调整结果只保存为打印设置，不改原件，也不改确认数据。

## 支付截图

- 手机支付截图，仅用于打印稿。它不参与材料盘点、字段提取、材料证据关联、查重，也不上传 ERP。
- 员工在确认页选中某张住宿发票，点「补充支付截图」上传；每张住宿发票至多一张。
- 点「去打印」时，若有住宿发票未补截图：提醒，但允许打印；该页下半页只放结账单。

## ERP 填报

「去报销」进入现有的自动填报：浏览器 CDP 驱动、导入发票、写明细、保存草稿、严格回读，结果不确定即停并对账。变化只有两处：

- 页面接管原来的 `tell_user`：打开专用 Chromium 后，页面提示员工在该窗口登录，登录完成后点「继续」。
- 出租车照片与其他发票一样走发票识别导入，上传**原图**；矫正图只用于打印。

## 与既有 ADR 的关系

- **修订 ADR-0001、ADR-0009**：Skill 外壳和「模型只执行 `next`」让位于本地应用。内核判定下一步的原则不变，只是消费方从模型换成页面和服务端。
- **取代 ADR-0011（MarkItDown）中的 Agent 候选**：文本 PDF 的字段候选改由规则解析器产生，MarkItDown 不再是必经环节。
- **修订 ADR-0011（受管 OCR）与 ADR-0004**：图片路径从「默认模型视觉」改为「OCR + 规则，失败转手工补填」，不再有模型视觉回退。
- **ADR-0010 的命令守卫**失去防模型的必要性，但保留无害；实施时再决定是否移除。
- **保持**：Node 内核零 npm 依赖（打印稿生成器放在独立 package）、空文本 PDF 必须阻塞、ERP 写入不重放、对账后只有原地等待和转人工两种处置。

实施前应补一条新的 ADR 记录上述取舍，并在 `CONTEXT.md` 中补充「打印稿」「支付截图」两个术语，同时修订「材料盘点」的边界表述。

## 建议实施顺序

1. **统一业务序号**：改内核排序，明细行和材料包先一致，现有 Skill 流程即可受益。
2. **规则解析器**：四类材料解析器加二维码核对，以本机样本做测试夹具；夹具须脱敏后才能入库。
3. **本地应用骨架**：服务端自动推进 `run` 步骤，上传页、手工补填页和整单明细确认页。
4. **打印稿**：`packages/print-sheet`、预览页、支付截图补充入口。
5. **接入 ERP 填报**：「去报销」复用现有写入链路，页面接管登录提示；然后下线 Skill 入口。
