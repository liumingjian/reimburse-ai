# 报销用户交互契约

## 目标

`baox` 面向公司的所有报销员工。员工看到的是稳定、简短、可执行的系统反馈，不需要理解模型、材料读取、浏览器自动化或报销系统内部处理过程。

每次响应由内核生成固定模板，模型只负责按 `step.kind` 执行动作并原样传递 `speak` 或 `step.prompt`。模型不能改写固定话术，也不能自行创造确认方式。

## 响应结构

每次 `next` 响应包含：

- 当前报销人和任务信息；
- `progress.phase/of/label`，使用稳定的业务阶段编号；
- `interaction.templateId/version/status`，只用于日志、测试和版本追踪，不展示给员工；
- 固定的 `speak`；
- 用户需要处理时才提供固定的 `step.prompt`、表格或下一步。

员工可见内容只允许使用业务插槽，例如报销人、常驻城市、材料名称、金额、日期、项目和待处理事项。绝对路径、命令参数、状态枚举、模型或组件名称、内部标记、原始错误码不属于员工话术。

## 业务进度

| 阶段 | 名称 |
| --- | --- |
| 1/10 | 环境准备 |
| 2/10 | 身份与常驻城市 |
| 3/10 | 材料盘点 |
| 4/10 | 材料整理 |
| 5/10 | 划分费用事件 |
| 6/10 | 项目归属 |
| 7/10 | 报销信息核对 |
| 8/10 | 报销材料准备 |
| 9/10 | 保存报销草稿 |
| 10/10 | 草稿交接 |

当前代码尚未把报销系统草稿写入接到 `next` 的提交链路；已有流程会在准备材料交接后停止。后续接入写入时，仍必须沿用这组编号，不能把内部动作名称直接变成员工阶段名称。

## 常驻城市

常驻城市统一使用“常驻城市”，不使用“常住城市”或其他同义词。

首次使用：

1. 没有城市参考时，直接提示员工输入常驻城市；输入后继续。
2. 有可信的城市参考时，展示该城市。员工回复「确认」表示接受；不正确时直接输入自己的城市。
3. 直接输入的新城市覆盖当前员工默认值，不再二次确认。

城市参考由上游环境提供，可通过 `homeCitySuggestion` 传入；没有可信来源时不猜测、不从材料反推，直接走填写城市的路径。

再次新建报销：在创建任务前展示“报销人”和“常驻城市”。员工回复「确认」直接继续；如果城市不正确，直接输入新城市并覆盖默认值，然后继续。

已经开始的任务保留创建时的城市快照。新任务在确认或修改后取得最新默认值。

## 固定确认

普通确认统一要求员工在当前会话中回复「确认」。不把“好的”“没问题”“继续”等表达自动当作确认。城市修正是直接输入城市，不提供通用“修改”指令；普通流程不提供通用“取消”指令。明确的任务作废是独立的生命周期操作。

确认材料时，固定结构为：当前状态、已完成内容、员工需要做什么、下一步。没有员工动作时省略最后两项中的动作部分。开放项合并成一张表，一次只给一个下一动作。

## 异常模板

- `needs_adjustment`：列出需要员工补充或调整的事项，处理完成后重新核对。
- `temporarily_unavailable`：说明系统暂时无法继续，给出恢复方向；不会暴露内部原因，不会假装完成。
- `human_review`：固定说“当前报销已暂停，材料和状态已保留。请在报销系统中核对；如无法判断，请联系报销管理员。”

未知的保存结果不自动重试，固定提示员工先在报销系统中核对，不要重复操作。恢复流程由内部执行壳处理，员工只看到业务状态。

## 自动保存边界

后续接入报销系统写入时，员工在项目选择页提交任务选择即构成“保存报销草稿”的授权，不再追加“确认保存草稿”问题。自动保存只允许保存草稿，不得自动提交审批、付款、审计或删除。保存成功固定提示：“报销草稿已保存。请打开报销系统检查，是否提交由你决定。”

## 变更与验收

修改话术必须同时更新模板实现、本文档和黄金对话测试。测试必须覆盖首次使用、再次使用、城市修改、用户待办、暂时不可用、人工核对、自动保存和保存结果未知，并检查同一状态与输入产生相同结构、模板版本和允许插槽。
