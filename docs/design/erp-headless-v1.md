# 去报销稳定性：无头执行器 v1

状态：2026-10-11 与所有者逐项确认。决策见 [ADR-0033](../adr/0033-headless-executor-with-hosted-erp-credentials.md)
与 [ADR-0034](../adr/0034-automatic-re-run-before-the-draft-is-saved.md)；两者都在下文验证计划通过后生效。

2026-10-12 修订（所有者）：执行器跑在**员工自己的电脑上**，不在服务端。用无头、专用有头浏览器还是员工自己 Chrome 里的扩展，
按 S8 实测，哪种更稳定、更快就用哪种。下文凡说「服务端」「主机」运行浏览器的地方，都按员工电脑理解。
S8 已选定无头，见 [S8 的结果](#s8-的结果2026-10-12测试环境-mac-mini)。

## 起因

去报销整体能跑通，但不稳定：最常见的是遇到异常后停下，给出提示，要人工介入。2026-10-11 审查了扩展、执行器和
服务端编排。结论是重复写入 ERP 这一块守得很好，不稳定主要来自另一个方向：把「不确定」当成「失败」，
再加上有头浏览器要面对的人为因素和系统因素。

## 已确认的方向

1. **第一版只做无头路径**（ADR-0033）。服务端无头 Chromium 用员工托管的 ERP 凭据登录。去报销以暂存草稿交接，
   终态是 ERP 草稿已交接。每个任务结束后登出。允许挤掉员工已有的 ERP 登录。并发上限 2，按先来先服务排队。
2. **暂存前自动重新去报销**（ADR-0034）。最多 2 次。每次重跑前用 WebAPI 只读确认发票没有被已保存的单据占用。
   暂存开始之后，只通过 WebAPI 按归属标记对账。
3. **明细第一版仍按页面填写，回读做两道。** 一道是页面回读，另一道在暂存后用 WebAPI `View` 读模型，两道一致才算通过。
   WebAPI 写入以后再评估。
4. **不做**：
   - ADR-0029 的删除草稿网关；
   - 按行断点续填，由第 2 条取代；
   - 扩展专属的加固项（C、D2–D3）；
   - 有头和无头之间的可配置项，留到后续版本。
5. **失败现场包**：
   - 逐动作轨迹：命中的元素、坐标、耗时、当时的弹窗；
   - 每个关键步骤后截图；
   - 保存在服务端，随报销任务的可见性走，默认保留 14 天。

## 工作拆分

### 线 1：执行器与服务端加固，两条路径都受益，现在就做

1. **D1**：远程执行器在 `resuming` 期间断线时仍要启动重连窗口；服务端为每个 ERP 任务加整单截止时间，到期按有无尝试分别收口。附复现测试。
2. **B1**：导入等待期间，先识别并消掉已知的通知（`notices.ts`），只有认不出的弹窗才算 ERP 的回答。
3. **A1**：`waitFor` 在截止时间内吞掉单次读取失败，继续观察；连续失败才抛出。
4. **A2**：
   - 固定等待全部改为条件等待；
   - 计数重试改为按截止时间重试；
   - 截止时间按实测的 ERP 响应速度伸缩，替换掉写死的 `DEFAULT_PACE`；
   - 断线期间暂停计时。断线只出现在扩展路径，可以晚做。
5. **B2、B3**：
   - 写格子前后都检查会话和遮挡；
   - 发现登出时报「ERP 会话丢失」，不再报找不到字段；
   - 点完「不生成费用明细」后核实模式。
6. **E1**：实现失败现场包。
7. **E2**：加故障注入用例，覆盖页面读失败、闲置提示、会话丢失、导入后无回执、暂存前中断后自动重跑。

### 线 2：无头路径，验证通过后开工

1. ERP 凭据：设置页、加密存储、试登录、失效处理，以及去报销前的挤号提示。
2. 员工电脑上浏览器的生命周期：持久的配置目录，任务开始时登录、结束时登出。一台电脑一次只跑本人的任务，不再有主机并发上限和排队。
   扩展无法启动进程，所以 S8 选定的无头浏览器要在每台电脑上新增一个本地组件。
   员工看不见无头页面：首次登录或会话失效时要有个可见的登录过渡，要人工看一眼时要附截图，不能再说「看一眼标签页」。
3. 执行器补上暂存动作（作为 ERP 动作尝试）、事由里的归属标记、WebAPI `View` 模型回读。
4. 自动重新去报销，以及 WebAPI 发票占用查询（ADR-0034）。
5. 对账改为按归属标记通过 WebAPI 查找草稿。
6. 无头浏览器所需本地组件的分发与升级：随扩展下载，还是单独安装。

#### 线 2 的进展（2026-10-12）

**第 2 项的骨架：本地执行器**（`local-executor/`，`@baox/local-executor`）。它是员工电脑上一个独立的 Node 进程。
- **对服务端来说，它就是又一个浏览器扩展。**
  - 用同一个配对码配对，连同一条通道；
  - 接 `erp.fill` / `erp.reconcile`，经扩展的 `job-link` 回报事件；
  - 断线时在重连窗口内恢复。

  服务端一行没改。
- **每个任务的流程：**
  1. 在持久配置目录上启动一个自己的无头 Chromium；
  2. 执行器探测到登录页，就用 ERP 凭据登录（`erp-executor/src/sign-in.ts`）；
  3. 跑 `runFillJob`；
  4. 无论结果如何，都用 WebAPI 登出，并关掉浏览器。
- **一台电脑一次只跑一个任务。**
- **登录**（`signIn`）只保留 S2/S8 实测证明必要的处理：
  - 等登录页初始化完；
  - 预取主控台脚本；
  - 遇到「语言未加载」时确认后重交；
  - 遇到「该帐号已登录在线」时确认；
  - 点了没反应时重交。

  ERP 拒绝的登录不会再交，以免锁住账号。出现第二道校验也直接停下。
- **执行器的改动：** `runFillJob` 和 `runReconcileJob` 新增可选端口 `signIn`。扩展不传这个端口，行为不变，仍然停在 `waiting_login`。
- **对账：** 浏览器随任务关掉，未暂存的新增单也随之消失，所以对账读到的是一个新的主控台。这对那张单来说如实。
  按归属标记查草稿是第 5 项。

运行方式（ERP 凭据在应用的设置页保存，随每个任务下发）：

```sh
pnpm --filter @baox/local-executor start pair --origin http://<应用地址> <配对码>
pnpm --filter @baox/local-executor start run
```

**实测**（Mac mini，真实测试发票，只读）：`server/scripts/spike-local.ts` 用 S8 的替身应用和本地执行器的命令行配对，
每轮发一个 `erp.fill`。替身在 `attempt_started` 处刹住，所以不导入、不保存。

- 前 3 轮全部通过：
  - 到刹车点 36–50 秒，含启动浏览器和登录；
  - 登录约 6 秒。配置目录冷缓存的第一次是 54 秒；
  - 每轮都登出（HTTP 200），结束后没有残留的浏览器进程。
- 随后 10 轮里过了 9 轮：
  - 到刹车点 37–64 秒，中位数约 40 秒；
  - 10 次都登出，没有残留进程。
- 第 9 轮失败在打开新增单：页面上有两个可见的「新增」，执行器拒绝猜测，以 `CHROMIUM_TARGET_NOT_FOUND` 中止。
  这一步在任何写入之前，浏览器照样登出并关掉了。
  - 疑点：#395 的「点了没反应就再点」在「我的费用报销」生效慢时多点了一次，把列表开了两份。
  - 这次实测没有抓现场，下一步先给 `spike-local.ts` 接上 S8 的 `navigationScene` 再查。

**暂存是无头路径能交付的前提（第 3 项）。** 员工看不见无头浏览器，任务结束时浏览器一关，未保存的新增单就丢了。
在暂存做完之前，本地执行器不对员工开放。

**S5 实测暂存**（2026-10-12，所有者同意，Mac mini，测试账号，`--save`）：S2、S4 通过后，S5 在 S4 那张单上点了「暂存」。
- 「暂存」在「保存」的下拉里（`tbSaveTemp`），悬停箭头后点到了。没有弹出对话框。
- 页签标题从「新增」变成「修改」，**但单据编号一直是空的**，60 秒后 S5 以 FAIL 收场。暂存单在这个 ERP 上不分配单据编号，
  编号要等员工保存时才生成。
- 新加的只读检查 S9 用 `ExecuteBillQuery` 查当天的暂存单（`FDocumentStatus = 'Z'`），找到了这张：内码 119945，
  单据编号为空白，单据状态 Z。按内码 `View` 0.7 秒读回整张单，收票分录 1 行、费用明细 1 行，和页面一致。
- S4 没有填事由，所以这张草稿的事由是空的。
- 这张测试草稿留给所有者在 ERP 里删除。

**由此定下的第 3 项做法：** 暂存单只能靠内码找回，单据编号不可靠，所以归属标记是必需品，不是可选项。
1. 填单时把 ADR-0029 的归属标记写进事由；
2. 点「暂存」（ERP 动作尝试），等页签变成「修改」；
3. 用 `ExecuteBillQuery` 按归属标记查出暂存单的内码，必须恰好一张；
4. 按内码 `View`，表头和分录与计划、与页面回读都一致，才算交接。

对账（第 5 项）用同一条查询。术语表里「ERP 草稿已交接」原先写的是「ERP 上已有单据编号」，已按实测改正。

**第 3 项已做（2026-10-13，所有者同意 `--save` 实测、测试草稿由 baox 删除）：**
- **只在无人值守路径上暂存。** 服务端把任务发给本地执行器时，在计划里加 `draft.mark`：`baox-` 加十位，由任务号算出，
  重发也一样。浏览器扩展的计划没有它，仍按 ADR-0028 不保存交接。
- **执行器（`erp-executor/src/draft.ts`）是唯一按暂存的模块。** 测试扫描源码：只有它点名 `tbSaveTemp`，
  没有模块点名保存、提交、审核、删除的命令或 WebAPI。
- **流程：**
  1. 事由写成「用途 + 空格 + 标记」，填写和严格回读照旧；
  2. 交接门通过后，先记下 `save` 动作尝试（带标记），落库后才按暂存；
  3. 悬停「保存」的箭头打开下拉，点 `tbSaveTemp`「暂存」，等页签变成修改；
  4. 按标记查暂存单，必须恰好一张；
  5. 按内码 `View`，和服务端判过的页面回读逐格比；
  6. 结果 `drafted`（ERP 草稿已交接），带内码。

  按下暂存之后的任何其他结局都是 `unknown`。
- **服务端：** `drafted` 是终态，完成页说明去「我的费用报销」打开暂存单。暂存后结果不明时只给转人工：
  对账要等第 5 项按标记查草稿，在那之前重新去报销可能再生出一张草稿。
- **实测**（Mac mini，测试账号，测试发票；S11 用执行器自己的暂存入口，事后删除自己的草稿）：
  - 第一次：暂存成功，但页签读作「费用报销单 - 修改」（带空格），执行器只认不带空格的写法，判成没有表单。
    S9 找到这张草稿（内码 119950），S10 删除。读页签已改为两种写法都认，假 ERP 也改成带空格。
  - 第二次：1.8 秒变成修改；按标记找到唯一一张（内码 119953，无单据编号，状态 Z）；
    `View` 的事由、收票 1 行、明细 1 行都对得上；草稿已删除。
  - 只对不上 8 列：收票的发票状态、是否勾选、是否勾选认证、查验状态、发票是否有修改、发票类别，明细的发票类型、
    费用承担部门。页面显示的是枚举或部门的名称，模型里是代码。这些列不再比，由页面回读负责。
  - 明细只测了新增单默认的那一行。填满明细的整单暂存，要等能跑完整去报销的实测环境。
- **第 9 轮那次失败的现场：** 本地执行器在导航失败或登录状态读不出时，把页面现场（菜单路径上的文字与位置、
  浮层、页签、登录框）写进本机日志，再登出。10 轮复测 8 轮通过，「两个新增」没有再出现。另外 2 轮停在登录探测
  （`erp_login_unknown`），这一类现在也会留下现场。

**ERP 凭据（第 1 项），所有者 2026-10-12 定：** 由服务端加密托管，每个任务随 `erp.fill` / `erp.reconcile` 下发给本地执行器，
本机不落盘。只发给本地执行器，不发给浏览器扩展。试登录也要经本地执行器在员工电脑上做，因为 `10.250.0.222` 不操作 ERP。

做法（见 ADR-0033 的修订）：
- **设置页「ERP 凭据」一节：**
  - 填账号和密码，点「保存并试登录」；
  - 保存后只显示账号和状态，不再显示密码；
  - 可以再试登录、换一组、清除；
  - 保存前提示挤号。
- **服务端：**
  - `erp_credential` 表每个应用账号一行，密码用 AES-256-GCM 加密，并绑定应用账号；
  - 密钥文件由 `install.sh` 生成，放在 `etc/` 下，不在数据目录里；
  - 状态有四种：未保存、未试登录、试登录成功、被 ERP 拒绝（密码已删除）。
- **配对记下是谁：** 本地执行器配对时自报 `local_executor`，旧扩展一律算浏览器扩展。
- **去报销前：** 配对的是本地执行器而凭据未试登录成功时，在建任务之前拒绝，提示去设置页。
  任务里 ERP 拒绝登录，同样立刻删除密码。
- **本地执行器** 不再读环境变量。新增 `erp.trySignIn` 处理试登录：
  1. 用自己的浏览器登录；
  2. 如果配置目录本来就是登录状态，先登出再用这组凭据登录；
  3. 登出，关闭浏览器。
- **还没做：** 去报销页面上的挤号提示，目前只在设置页保存时显示。

| S5 | 暂存和模型回读 | 暂存后拿到单据编号，`View` 读回的表头和分录与页面回读一致；所有者事后删除这张测试草稿 |
| S6 | 发票占用查询 | 用 `ExecuteBillQuery` 能查到某张发票是否被已保存的单据占用 |
| S7 | 资源占用 | 单个任务峰值内存 ≤ 500 MB |
| S8 | 选执行方式 | 同一张测试单在 Mac mini 上分别用扩展、专用有头浏览器、无头浏览器各跑多次，比较成功率和耗时；更稳定、更快的胜出 |

S2、S3、S4 任一不通过，ADR-0033 不生效，回到扩展路径并恢复线 2 之外的扩展加固项。S5 或 S6 不通过只影响 ADR-0034
和模型回读，不影响无头本身。

### 怎样运行

脚本是 `server/scripts/spike-headless.ts`，在 Mac mini 上用普通用户运行（root 下 Chromium 不加 `--no-sandbox`
不肯启动）。先装好 Chromium，或用 `--chromium` / `BAOX_CHROME` 指定可执行文件。

```sh
set -a; . ~/.baox-erp-live.env; set +a      # BAOX_ERP_TEST_ACCOUNT、BAOX_ERP_TEST_PASSWORD，可选 BAOX_ERP_TEST_TENANT
# 第一轮：只读，S4 跳过
pnpm --filter @baox/server exec tsx scripts/spike-headless.ts
# 第二轮：带测试发票，暂存一张草稿，两个会话并发
pnpm --filter @baox/server exec tsx scripts/spike-headless.ts \
  --invoice /绝对路径/测试发票.pdf --save --concurrency 2
```

- **环境变量**：
  - 账号密码只从 `BAOX_ERP_TEST_ACCOUNT` / `BAOX_ERP_TEST_PASSWORD` 读，不打印，不写进报告，也不走命令行；
  - `BAOX_ERP_TEST_TENANT` 可选，S2 用它核对登录后落在哪个账套；
  - `BAOX_ERP_ORIGIN` 覆盖 ERP 地址，默认取 `server/src/erp/config.ts`。
- **只读是默认**：
  - S4 要 `--invoice` 才跑。它把一张发票导入一张不保存的新增单，结束后关掉，「是否保存」答「否」。
    单据本身不留下，但「发票导入单据」会在 ERP 里生成或覆盖这张发票的收票单（ADR-0026）。
  - S3 要人在场：脚本会提示所有者先在自己的浏览器登录，再回答自己的页面有没有被登出，然后重新登录。
    加 `--non-interactive` 时跳过。
- **`--save`** 只影响 S5：在 S4 那张单上点「暂存」，打印单据编号，再用 `View` 读回，和页面回读比对。
  **这张测试草稿要所有者事后在 ERP 里手工删除**，脚本不删除任何单据，也不点保存、提交、审核、删除。
- **其他参数**：
  - `--bill <单据编号>`：一张已保存、带发票的单据，作为 S6 的对照；不带 `--save` 时 S5 只读 `View` 它。
  - `--invoice-no <号码,…>`：S6 额外查询的发票号码。
  - `--only S1,S2`：只跑选中的检查。
  - `--out <目录>`：报告目录。
  - `--prefetch`：登录前先把主控台的大脚本取进浏览器缓存，原因见下面「S2 的结果」。链路慢时要加。
  - `--only S9 --drafts-since "YYYY-MM-DD HH:mm"`：只读，列出这之后创建的暂存单（内码、有无单据编号、创建时间），
    并按内码 `View` 每一张。用来找回 S5 留下、没有单据编号的测试草稿。
- **结果**：
  - 每项打印一行 PASS / FAIL / SKIP 和原因；
  - 报告目录（默认在运行命令的目录下 `spike-report-<时间>/`）里有 `report.json` 和每一步的截图。
    报告只记形状、计数和耗时，不记金额、姓名和发票号码，S5 草稿的单据编号除外。
    截图是真实画面，交给别人之前先看一眼。
- **收尾**：脚本结束时（含 Ctrl-C）登出它自己创建的 ERP 会话，关掉它启动的所有浏览器，删除临时配置目录。

### S2 的结果（2026-10-12，测试环境 Mac mini）

无头登录本身没有问题，卡住登录的是链路带宽：

- 点「登录」后 `UserService.ValidateLoginInfo` 返回 200，接着页面用 RequireJS 加载主控台脚本。
  `kdformjsloader.min.js` 把 RequireJS 的 `waitSeconds` 设为 30。
- `kendo.all.min.js`（2.8 MB）和 `k3cloud.min.js`（3.4 MB）不压缩、没有 `Cache-Control`。
  Mac 到 ERP 只有 40–75 KB/s，每个都要 29–67 秒。
- 超过 30 秒，RequireJS 放弃，登录静默停住：要么一直停在登录页，要么停在 `dform.aspx` 的转圈上。
  没有报错，也没有未返回的请求。
- 不预取：0/9 通过。只预取 `kendo.all`：2/3。预取两者（`--prefetch`）：5/5，84–105 秒进入主控台，每次都确认已登出。
- 先前怀疑过的无头 UA 不是原因。「语言未加载」在这一轮没有再出现；脚本已能识别它、点确定并重新提交。

### S8 的结果（2026-10-12，测试环境 Mac mini）

**选定无头**（所有者，2026-10-12）。无头最快；它对员工无感知，员工也无从在执行中途误点 ERP 页面。

脚本是 `server/scripts/spike-modes.ts`。三种方式跑同一个 `runFillJob`、同一张测试发票，只换浏览器：

- 扩展：员工自己 Chrome 里的扩展，走去报销 → 在扩展开的标签页里登录 → 我已登录，继续；
- 专用有头、无头：Chrome for Testing 加持久配置目录，经 CDP 驱动。

每次走到登录探测 → 核对 → 新增单 → 发票助手 → 上传识别勾选，停在「发票导入单据」之前：替身应用对
`attempt_started` 回 `{persisted:false}`，执行器拒绝继续。不导入，不保存，收尾关掉助手和新增单（「否」）并登出。

```sh
set -a; . ~/.baox-erp-live.env; set +a
pnpm --filter @baox/server exec tsx scripts/spike-modes.ts --invoice /绝对路径/测试发票.pdf \
  --rounds 3 [--modes headless] --prefetch --chromium <Chrome for Testing 可执行文件>
```

第 0 轮是预热，不计入；每轮轮换三种方式的先后。Chrome for Testing 要加 `--disable-field-trial-config`
（脚本已加），否则它的实验配置会以 `ERR_BLOCKED_BY_CLIENT` 拦掉内网 ERP。

| 方式 | 成功（不含预热） | 到导入前（中位） | 其中打开新增单 | 其中上传识别 | 峰值内存 |
|---|---|---|---|---|---|
| 无头 | 10/13 | 30–31 秒 | 15–18 秒 | 13–15 秒 | 约 1.5 GB |
| 专用有头 | 1/3 | 42 秒 | 19–27 秒 | 14–16 秒 | 约 1.6 GB |
| 扩展 | 2/3 | 42 秒 | 26–29 秒 | 13–14 秒 | 约 2.0 GB |

- 上传识别三者一样。扩展慢在打开新增单：它总在新标签页里从头加载主控台。
- 峰值内存都超过 S7 的 500 MB。
- 失败有两类，与选哪种方式无关（已修，见「修复之后」）：
  - **打开新增单不稳**（无头 3/13、有头 2/3）：找不到唯一的「员工服务」或「新增」，或点过「新增」后 45 秒内
    新增单没有出现。只在 CDP 两种方式出现，登录后紧接着点菜单；扩展从未在这一步失败。原因未查明：报错
    `CHROMIUM_TARGET_NOT_FOUND` 丢掉了匹配数，分不清是没找到还是多于一个，先要补上它。
  - **登录探测的竞态**（扩展 2/8，含冒烟）：标签页加载完、登录表单还没画出来的一刻，`probeIdentity`
    读不出身份就立即放弃（`erp_login_unknown`），没有在等待时间内重试。无头在任务开始时自己登录，同样经过这一刻。
- **修复之后**（同日，同一张发票，只读到导入前）：两类失败都已修掉，见下。无头 8/8、扩展 8/8（均不含预热，
  预热也通过），到导入前中位都是 30–31 秒，扩展峰值内存约 2.0 GB、无头约 1.5 GB。无头仍是选定的方式：两者
  一样快、一样稳之后，余下的区别是员工看不看得见、碰不碰得到。
  - 登录探测：`unknown` 在等待时间内再看，等完仍是 `unknown` 才交给人。
  - 打开新增单：路径上的每一次点击（主菜单、员工服务、我的费用报销、新增）都等它的结果，没有就再点，同一预算
    内最多三次。诊断现场：一次主菜单没展开（「员工服务」在页面里但不可见），一次列表已开、「新增」唯一可见，
    点了没出新单；两次都没有遮罩或对话框。`CHROMIUM_TARGET_NOT_FOUND` 现在带上匹配数。
  - 测量本身的一个坑：Chrome 把解包扩展的 service worker 脚本留在配置目录里，版本号不变时重启后照旧运行旧的
    执行器。脚本在扩展模式启动前删掉 `Default/Service Worker`。
- 冒烟（不带发票，只到核对）：扩展 4/5、有头 5/5、无头 4/5，各自 1 秒左右。无头那次失败是登录页整页空白 60 秒，
  页面已加载、请求都已返回。

## 留到验证之后再定

- 已定（2026-10-12，所有者）：执行器沿用持久的浏览器配置目录，主控台脚本在第一次登录后留在缓存里。
  这两个脚本没有 `Cache-Control`，`Last-Modified` 是 2021 年，浏览器按启发式规则长期直接用缓存。

  那一次要么先预取（同 `--prefetch`），要么接受失败后重来。员工自己的 Chrome 早就缓存了这些脚本，
  所以扩展路径从没遇到这个问题。
