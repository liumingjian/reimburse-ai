# 去报销稳定性：无头执行器 v1

状态：2026-10-11 与所有者逐项确认。决策见 [ADR-0033](../adr/0033-headless-executor-with-hosted-erp-credentials.md)
与 [ADR-0034](../adr/0034-automatic-re-run-before-the-draft-is-saved.md)；两者都在下文验证计划通过后生效。

## 起因

去报销整体能跑通，但不稳定：最常见的是遇到异常后停下，给出提示，要人工介入。2026-10-11 审查了扩展、执行器和
服务端编排。结论是重复写入 ERP 这一块守得很好，不稳定主要来自另一个方向：把「不确定」当成「失败」，
再加上有头浏览器要面对的人为因素和系统因素。

## 不稳定因素地图

| # | 因素 | 代码位置 | 后果 | 无头后 |
|---|---|---|---|---|

| A2 | 固定等待和固定次数，不随 ERP 快慢伸缩（事由写后等 1.2 秒，金额约 3 秒，下拉 2 秒，上传 9.6 秒） | `erpform.ts:559`、`draft-flow.ts:357`、`erpform.ts:486`、`steps.ts:403` | 慢时误报失败 | 仍需修 |
| A3 | 登录探测见到 `readyState=complete` 就下结论 | `probe.ts:141` | 慢 ERP 上误报登录状态未知 | 改为凭据登录后的就绪判定 |

| E1 | 失败时只截一张图，没有逐动作轨迹，扩展日志随 Service Worker 消失 | `steps.ts:700`、`job.ts:85` | 偶发失败无法复盘 | 仍需修 |
| E2 | Web e2e 只有 3 条 ERP 用例，假 ERP 有 41 条未实测假设 | `web/e2e/server/erp.spec.ts`、`testing/fake-erp.ts` | 失败路径无测试 | 仍需修 |

## 已确认的方向

1. **第一版只做无头路径**（ADR-0033）。服务端无头 Chromium 用员工托管的 ERP 凭据登录。去报销以暂存草稿交接，
   终态是 ERP 草稿已交接。每个任务结束后登出。允许挤掉员工已有的 ERP 登录。并发上限 2，按先来先服务排队。
2. **暂存前自动重新去报销**（ADR-0034）。最多 2 次。每次重跑前用 WebAPI 只读确认发票没有被已保存的单据占用。
   暂存开始之后，只通过 WebAPI 按归属标记对账。
3. **明细第一版仍按页面填写，回读做两道。** 一道是页面回读，另一道在暂存后用 WebAPI `View` 读模型，两道一致才算通过。
   WebAPI 写入以后再评估。
4. **不做**：
   - ADR-0029 的删除草稿网关；
   - 按行断点续填，由第 2 条取代；
   - 扩展专属的加固项（C、D2–D3）；
   - 有头和无头之间的可配置项，留到后续版本。
5. **失败现场包**：
   - 逐动作轨迹：命中的元素、坐标、耗时、当时的弹窗；
   - 每个关键步骤后截图；
   - 保存在服务端，随报销任务的可见性走，默认保留 14 天。

## 工作拆分

### 线 1：执行器与服务端加固，两条路径都受益，现在就做

1. **D1**：远程执行器在 `resuming` 期间断线时仍要启动重连窗口；服务端为每个 ERP 任务加整单截止时间，到期按有无尝试分别收口。附复现测试。
2. **B1**：导入等待期间，先识别并消掉已知的通知（`notices.ts`），只有认不出的弹窗才算 ERP 的回答。
3. **A1**：`waitFor` 在截止时间内吞掉单次读取失败，继续观察；连续失败才抛出。
4. **A2**：
   - 固定等待全部改为条件等待；
   - 计数重试改为按截止时间重试；
   - 截止时间按实测的 ERP 响应速度伸缩，替换掉写死的 `DEFAULT_PACE`；
   - 断线期间暂停计时。断线只出现在扩展路径，可以晚做。
5. **B2、B3**：
   - 写格子前后都检查会话和遮挡；
   - 发现登出时报「ERP 会话丢失」，不再报找不到字段；
   - 点完「不生成费用明细」后核实模式。
6. **E1**：实现失败现场包。
7. **E2**：加故障注入用例，覆盖页面读失败、闲置提示、会话丢失、导入后无回执、暂存前中断后自动重跑。

### 线 2：无头路径，验证通过后开工

1. ERP 凭据：设置页、加密存储、试登录、失效处理，以及去报销前的挤号提示。
2. 服务端无头 Chromium 的生命周期：每个任务一个独立的浏览器上下文，任务开始时登录、结束时登出，并发上限 2，排队可见。
3. 执行器补上暂存动作（作为 ERP 动作尝试）、事由里的归属标记、WebAPI `View` 模型回读。
4. 自动重新去报销，以及 WebAPI 发票占用查询（ADR-0034）。
5. 对账改为按归属标记通过 WebAPI 查找草稿。
6. 原生依赖引导把 Chromium 装到内网主机上。

## 验证计划

由我写脚本，所有者在 `10.250.0.222` 上用自己的 ERP 账号运行。脚本默认只读，暂存那一步要显式加参数才会执行。

| # | 要证明什么 | 怎样算通过 |
|---|---|---|
| S1 | 主机能访问 ERP 和发票助手（piaozone） | 两个域名都能连通，页面能加载 |
| S2 | 无头 Chromium 能用账号密码登录 | 不出现验证码或短信校验；账套选择能确定性完成；登录后主控台可用 |
| S3 | 挤号行为 | 所有者开着自己的 ERP 页，脚本登录后观察该页是否被登出；再反过来验证脚本会话被挤掉时，执行器能认出这是会话丢失 |
| S4 | 无头环境下发票助手能上传、识别、导入 | 1 张测试发票识别成功，导入后收票网格回读正确 |
| S5 | 暂存和模型回读 | 暂存后拿到单据编号，`View` 读回的表头和分录与页面回读一致；所有者事后删除这张测试草稿 |
| S6 | 发票占用查询 | 用 `ExecuteBillQuery` 能查到某张发票是否被已保存的单据占用 |
| S7 | 资源占用 | 单个任务峰值内存 ≤ 500 MB，两个任务并发时主机不触发 OOM |

S2、S3、S4 任一不通过，ADR-0033 不生效，回到扩展路径并恢复线 2 之外的扩展加固项。S5 或 S6 不通过只影响 ADR-0034
和模型回读，不影响无头本身。

### 怎样运行

脚本是 `server/scripts/spike-headless.ts`，在 `10.250.0.222` 上用普通用户运行（root 下 Chromium 不加 `--no-sandbox`
不肯启动）。先装好 Chromium，或用 `--chromium` / `BAOX_CHROME` 指定可执行文件。

```sh
set -a; . ~/.baox-erp-live.env; set +a      # BAOX_ERP_TEST_ACCOUNT、BAOX_ERP_TEST_PASSWORD，可选 BAOX_ERP_TEST_TENANT
# 第一轮：只读，S4 跳过
pnpm --filter @baox/server exec tsx scripts/spike-headless.ts
# 第二轮：带测试发票，暂存一张草稿，两个会话并发
pnpm --filter @baox/server exec tsx scripts/spike-headless.ts \
  --invoice /绝对路径/测试发票.pdf --save --concurrency 2
```

- **环境变量**：
  - 账号密码只从 `BAOX_ERP_TEST_ACCOUNT` / `BAOX_ERP_TEST_PASSWORD` 读，不打印，不写进报告，也不走命令行；
  - `BAOX_ERP_TEST_TENANT` 可选，S2 用它核对登录后落在哪个账套；
  - `BAOX_ERP_ORIGIN` 覆盖 ERP 地址，默认取 `server/src/erp/config.ts`。
- **只读是默认**：
  - S4 要 `--invoice` 才跑。它把一张发票导入一张不保存的新增单，结束后关掉，「是否保存」答「否」。
    单据本身不留下，但「发票导入单据」会在 ERP 里生成或覆盖这张发票的收票单（ADR-0026）。
  - S3 要人在场：脚本会提示所有者先在自己的浏览器登录，再回答自己的页面有没有被登出，然后重新登录。
    加 `--non-interactive` 时跳过。
- **`--save`** 只影响 S5：在 S4 那张单上点「暂存」，打印单据编号，再用 `View` 读回，和页面回读比对。
  **这张测试草稿要所有者事后在 ERP 里手工删除**，脚本不删除任何单据，也不点保存、提交、审核、删除。
- **其他参数**：
  - `--bill <单据编号>`：一张已保存、带发票的单据，作为 S6 的对照；不带 `--save` 时 S5 只读 `View` 它。
  - `--invoice-no <号码,…>`：S6 额外查询的发票号码。
  - `--only S1,S2`：只跑选中的检查。
  - `--out <目录>`：报告目录。
  - `--prefetch`：登录前先把主控台的大脚本取进浏览器缓存，原因见下面「S2 的结果」。链路慢时要加。
- **结果**：
  - 每项打印一行 PASS / FAIL / SKIP 和原因；
  - 报告目录（默认在运行命令的目录下 `spike-report-<时间>/`）里有 `report.json` 和每一步的截图。
    报告只记形状、计数和耗时，不记金额、姓名和发票号码，S5 草稿的单据编号除外。
    截图是真实画面，交给别人之前先看一眼。
- **收尾**：脚本结束时（含 Ctrl-C）登出它自己创建的 ERP 会话，关掉它启动的所有浏览器，删除临时配置目录。

### S2 的结果（2026-10-12，在 Mac 上，不是 10.250.0.222）

无头登录本身没有问题，卡住登录的是链路带宽：

- 点「登录」后 `UserService.ValidateLoginInfo` 返回 200，接着页面用 RequireJS 加载主控台脚本。
  `kdformjsloader.min.js` 把 RequireJS 的 `waitSeconds` 设为 30。
- `kendo.all.min.js`（2.8 MB）和 `k3cloud.min.js`（3.4 MB）不压缩、没有 `Cache-Control`。
  Mac 到 ERP 只有 40–75 KB/s，每个都要 29–67 秒。
- 超过 30 秒，RequireJS 放弃，登录静默停住：要么一直停在登录页，要么停在 `dform.aspx` 的转圈上。
  没有报错，也没有未返回的请求。
- 不预取：0/9 通过。只预取 `kendo.all`：2/3。预取两者（`--prefetch`）：5/5，84–105 秒进入主控台，每次都确认已登出。
- 先前怀疑过的无头 UA 不是原因。「语言未加载」在这一轮没有再出现；脚本已能识别它、点确定并重新提交。

## 留到验证之后再定

- 执行器怎样保证主控台脚本在 RequireJS 要它之前已在缓存里：沿用持久的浏览器配置目录，
  或登录前预取（同 `--prefetch`）。还要在 `10.250.0.222` 上实测链路：内网够快的话，这一条只是保险。
- `10.250.0.222` 访问 `http://erp.antute.com.cn/` 得到 HTTP 403，Mac 是 200；可能要走 `build.env` 里的代理或加白名单。
- S2 如果需要选账套：凭据里是否要多存一个账套字段。
- 主机 Chromium 的安装形态：系统包，还是随发布分发的固定版本。
