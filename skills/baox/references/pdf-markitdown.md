# 文本 PDF：MarkItDown 分支

这份参考只在 `baox next` 的 `step` 明确涉及文本 PDF 转换、Markdown 字段候选、候选 JSON 校验或 PDF 空文本处置时读取。主流程仍由内核决定；模型只执行 `step.argv`，不自行选择转换器、schema 或结果路径。

## 分支入口

先念 `speak`，从 `step` 读取本次 schema、材料身份、结果路径和回传 token。`run` 执行转换命令；`read_markdown` 先完成下面的候选提取，再逐字执行 `step.argv` 接收候选。

完成条件：内核返回成功结果，且结果文件路径、材料标识和当前 `stepToken` 与本次工单一致。退出码为 `2` 时照实报告 `blockedBy`，退出码为 `1` 时念 `error` 后停止。

## 运行时

文本 PDF 使用随 Skill 发布的 Python/uv 锁定运行时。环境准备先验证并同步 MarkItDown 到 `BAOX_HOME` 下的受管目录；图片分支的 `extract-reimbursement-images` OCR 运行时也在这里准备。解析阶段只消费已准备的运行时，不得首次同步或下载软件包，材料转换在本机完成。运行时路径和版本以工单及随包锁文件为准。

完成条件：锁定运行时成功产出通过内核校验的转换记录。缺少 uv、受管运行时、依赖同步失败或锁文件不匹配时，按内核提示修复环境；执行内核发出的安装命令，不手动换版本、绕过锁文件或改用全局 Python。PDF 转换使用本地默认转换器，插件和云端 OCR 保持关闭。

## 原件与派生物

原始 PDF 是报销材料。内核先固定 `materialId` 与原件 `contentHash`，再生成 Markdown；Markdown 是派生产物，不能替代原件、发票身份或材料范围。Markdown 另有由内核记录的哈希；模型不能填写或改写任何原件哈希、Markdown 哈希、转换器版本或材料元数据。

完成条件：候选结果仍绑定当前原件身份和 Markdown 派生物；任一哈希变化都会使旧候选、证据和后续确认失效并重新走内核步骤。

## Agent 候选

Agent 只从工单提供的 Markdown 文本提出字段候选，来源标记为 `agent_from_markdown`。按工单给出的 schema 写结果，不添加未声明字段，不把候选写成已解析事实。

- **主要发票只使用带编号 Markdown 的标题和金额标签。** 分别核对票种、不含税金额、税额、价税合计对应的文字或表头；仅靠同一行含有两个金额及加法守恒，无法排除净额与税额互换。Markdown 不能明确标签时保留缺失或歧义。
- `kindEvidence` 是必填的原生票种证据数组：引用票面标题或正文中的票种标记，例如普通发票、旅客运输服务、增值税专用发票、铁路电子客票、行程单或结账单；不要只引用金额或文件名。
- 每个非空字段给出精确原文片段和 1 基行号；片段必须是对应原始 Markdown 行的连续子串。
- `netAmount` 和 `taxAmount` 必须分别引用带表头可定位的金额/税额单元格，或带明确字段标签的单一金额；不要用同时包含两个金额的整行或跨列片段作为两者的共同证据。
- **跨行、串列或起终点归属不清时保留歧义。** 逐行核对 Markdown 中的表头、段序、起点和终点；仍不能确定时写 `null`，不打开 PDF 页图，也不把 PDF 转入图片读取。
- 无法从行序和表列确定归属时写 `null`，把字段名放入 `unreadable`，并留下可读的 `issues`；不靠地名常识、文件名、行程范围、申请日期或开票日期补值。
- 费用发生日只取票面行程日/入住日等材料事实；`issueDate` 与 `travelDate` 分开，开票日不能替代行程日。
- 金额使用两位小数字符串。只取有票面标签的合计、税额和不含税金额；明细行金额不自动当合计，不补算、不四舍五入、不把差额抹到某一段。
- 保留票面原生发票身份字段；没有代码就留空，不把号码重排或拼成另一种票种身份。
- `issues` 只记录仍需处置的问题，内核会据此阻塞。已核对的跨行归并、折扣合计选择等说明放在对应 `fieldBasis`；缺失字段用 `null` 和 `fieldStatus` 表达，由内核判断是否适用。例如全电发票没有代码、铁路票面没有净额和税额，都如实保留缺失；铁路费用明细的税额 `0.00` 由内核按业务规则产生，不伪装成票面读数。

完成条件：每个非空候选都有 Markdown 证据；主发票票种及三项金额已有明确文字或表头；跨行和串列无法确定的字段保留待办；候选 JSON 与工单 schema 严格一致。

## 内核校验

候选交回后由内核完成确定性校验：JSON 形状与额外字段、原件/Markdown 哈希、每条 quote 与行号、原生票种证据、带标签的净额/税额证据、字段格式、真实日期、金额精度与守恒、声明段数和逐段金额。证据片段存在只证明文本对应关系，不证明跨行地址、表格串列和起终点顺序的语义归属；这些歧义仍按候选状态保留。

完成条件：所有校验通过并形成当前材料版本的候选记录。任何校验失败都形成待确认项或阻塞，不把模型的“解析成功”当放行信号。

## 空文本与图片

MarkItDown 失败、产物为空或没有必要字段时，按内核返回的 `blockedBy` 处理；不能把空 PDF 当作已解析，也不能从文件名或尺寸猜票种、金额或日期。没有内核明确发出的 `read_images` 工单时，不把 PDF 擅自改走视觉读取；用户需要提供可读原件或按阻塞提示处置。

PNG/JPG 走独立图片字段提取步骤：先使用受管本地 OCR，仅对协调器明确标记的回退项使用模型视觉，并等待用户确认。图片读数与 Markdown 候选来源不同，不能互相伪装或用一个分支绕过另一个分支的确认。

完成条件：文本 PDF 空产物停在明确待确认项；图片只有在真正打开、结构校验通过且用户确认后才成为已解析值。

## 放行顺序

候选校验通过后，继续执行内核给出的分类、材料证据关联、事件与分摊步骤。行程单逐段金额与发票合计精确守恒时，由内核核对采用；否则由内核发出逐段金额提问。Agent 只提取材料上的金额，采用与税额切分均由内核决定。

材料事实、金额、日期、证据或哈希改变后，旧确认失效并重新全量检查。必须先完成 `classified_detail_confirmation`；用户确认分类明细后才进入项目簿和项目归属选择，项目号、费用项目和 ERP 放行不能提前发生。

完成条件：当前材料版本的所有待确认项、重复、证据关联、日期和金额校验均已清零，分类明细已由用户确认；在此之前不进入项目选择或 ERP 就绪。
